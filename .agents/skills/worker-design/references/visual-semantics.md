# 可读视图与语义

## 选择合适的表达

- 模块职责、依赖和状态归属：使用紧凑架构图或职责表。
- 事件触发、分支、恢复与循环：使用状态图。
- 多条件规则：使用决策表。
- 视觉层级和操作体验：使用可交互原型或真实操作材料。
- 一条规则或局部变更：直接写清楚，不强制绘图。

静态工程图优先 Mermaid 等可维护格式，不用图像生成工具代替精确关系。每个图只解释一个问题，默认不要超过五个节点横向并列。确需细节时拆分子图，并用稳定编号连接。

## 记录图的身份

随图保留：设计或模型标识、配置、视图映射版本、生成工具与版本、适用范围、证据引用、生成时间和省略内容。涉及实现时再记录对应源码与环境版本。

分别表达以下状态：

| 状态 | 可表达内容 |
| --- | --- |
| 拟议行为 | 正在讨论的设计承诺，未必实现 |
| 静态对应 | 已读取的代码路径与设计之间的关系 |
| 模型检查 | 给定模型、性质、假设和边界内的结果 |
| 实现验证 | 具体实现与环境上实际运行得到的结果 |
| 未知或过期 | 缺少依据，或相关对象变化后尚未重评 |

不要把它们合成“全绿”。引用旧运行报告时保留原始日期和对象，不能改成当前对象的通过标记。

## 投影不能改变语义

模型的多个具体状态可以投影到一个可读节点，但必须确认读者不会因此推断不存在的转移、独立性或终态。合并状态前核对：

1. 是否把允许与禁止的行为混成同一状态？
2. 是否隐去决定用户结果的守卫条件？
3. 是否制造了实际不可能的并行组合或退出循环的路径？
4. 是否丢掉导致违反性质的路径？
5. 是否隐藏了取消、故障或重试的提交边界？

有任何一项会改变判断，就拆分节点、补条件或显示局部细节。节点内不画的转移以及其他省略项要说明；无法确认投影保真时使用更直接的图形并标记限制。

## 解释反例

保留模型或运行输出的原始路径，再给人一个短场景：

- 初始条件；
- 按顺序发生的事件与可中断点；
- 被违反的具体承诺；
- 是设计问题、模型问题、假设冲突还是实现偏差；
- 修正后的实现义务与待验证场景。

示例中的人类可读标签只是说明。若没有实际检查，不得使用“验证发现”或“已经修复”的结果措辞。
