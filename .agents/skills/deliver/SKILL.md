# 推进整体交付

负责目标、任务图、调度与整体验收；专业方法由对应 worker 承担。沿用有效授权，先完成能自主推进的工作，只把确需人的取舍交回。

## 1. 找到当前工作

1. 读取项目约定、流程文档、长期上下文的相关部分、最近要求、既有决定、实际工具和当前成果；影响本次判断的旧结论回到当前来源核对。明确本次终点是调查、设计、验证、PR 就绪、合并、发布、部署或验收。
2. 复用已有工作记录。Spec 持续保存设计概览、共同约束、整体验收和 Ticket 目录；拆票后继续保留。目标清楚、影响局部且低风险的独立小改动，可在现有任务或 PR 中紧凑记录，不强制新建 Spec 或 Ticket。
3. 固定 `spec_ref` 的位置与有效修订、当前 Tickets 和依赖来源；代码使用提交或完整工作树身份，不能仅靠分支名、旧聊天或工作编号识别内容。
4. 读取 [共享记录与结果约定](references/work-contract.md)。沿用项目选定的权威来源；大功能或需要共同约束、依赖交接的工作，在分派实现前核对本批 Spec／Tickets 已实际保存并可读取。只有主目录、聊天分工或本地草案不算完成拆票。
5. 从当前项目发现检查、交付与协作能力；初始化可选，不要求先运行 `setup`。

同仓多个 Spec 或写入者并行时，读取 [本地并行约定](references/local-concurrency.md)，复用共同活动记录；顺序工作不额外建立协调流程。

## 2. 选择需要的能力

从足以交付的最短路径开始，按影响、失败后果和未知程度增减步骤，不按改动行数或是否开启 auto 分档：

| 情况 | 默认安排 |
| --- | --- |
| 目标明确、影响局部、低风险且易回退 | 直接实现与针对性检查；项目允许时，一位独立审查者分开完成需求和标准两轴，再走既定交付流程 |
| 原因或影响尚不清楚 | 先做能消除关键未知的最小调查；查清后回到适用的短流程 |
| 公共接口、权限、数据迁移或关键状态变化 | 补相关设计、消费者与兼容检查；值得建模的状态风险再使用 TLA |
| 大功能、多项可独立交付工作或协作依赖 | 保留共享 Spec，按清楚的部分逐步拆票；只并行真正独立的任务 |

每次新增发现或范围变化后重选路径；未知消除后撤掉不再需要的步骤。开始时用一句话交代本批安排，只有路线变化再补充，不让用户反复选择“轻量／完整”。同一 Agent 可承担实现与自查；复用仍适用的检查证据，不因换技能重复运行。保留项目规定的 CI、独立性和交付门槛。

| 当前工作 | 使用的技能或等价能力 |
| --- | --- |
| 查明问题、事实与范围 | `worker-investigate` |
| 明确行为、接口与架构 | `worker-design` |
| 确定视觉方向、界面与组件规格 | `worker-visual-design` |
| 把 Spec 拆成 Tickets，检查依赖与验收覆盖 | `worker-plan-tickets` |
| 检查值得建模的并发、重试或恢复设计 | `worker-tla` |
| 实现 Ticket、修正候选或构建／CI/CD 配置 | `worker-implement` |
| 按设计基准实现、修正或核对界面，检查连续动效 | `worker-ui-fidelity`；按任务区分修改与只读验收 |
| 为指定候选取得运行、流水线与验收证据 | `worker-verify` |
| 独立检查需求满足与项目标准 | `worker-review` |
| 推进 PR、反馈、CI 与授权内合并 | `worker-land` |
| 目标包含发布、部署与交付位置验收 | `worker-release` |
| 分派、消息、交接与协作恢复 | `collaborate` |
| 人需要掌握成果、架构变化或待决事项 | `brief` |
| 有明确范围的方法评估或工作流改进 | `worker-improve-workflow` |

按任务需要组合，不强制所有阶段、固定模型或并行数量。构建、CI/CD 配置只在目标需要时补齐，优先复用已有机制；没有远程 CI 或发布需求时，采用项目规定的本地检查与交付。同一 Agent 可在单任务中使用不同 worker；整份 Spec 并行推进时区分总控和各 Ticket 实现者，并保持独立审查。

能力可以替换。缺少某个 Skill 时使用已授权的等价方法并说明实际执行者，不冒称已调用；使用第三方 Skill 前核对版本和调用条件。`auto / challenge / steer / setup / guide` 仅由用户主动发起，不进入自动路由，也不通过读文件或委托绕过限制。

## 3. 按任务图持续调度

`worker-plan-tickets` 产出或修订任务图；本技能负责执行该图。不要把规划完成写成工作已经交付。

1. 核对每张待执行 Ticket 的目标、`acceptance_ids`、范围、产物和完成条件；未决设计不得靠拆票悄悄补成决定。发现缺口交回对应 worker，继续不受影响的任务。
2. 根据当前证据计算就绪任务：每条 `depends_on` 指定的前置任务或产物已达到约定释放条件，版本仍适用；授权、工具、当前归属和写入范围允许开始。
3. 再判断并行安全。接口、数据迁移、共享资源和集成顺序可能仍有冲突；文件不重叠或票号靠前不足以证明可并行。同一可写工作区或独占产物保持一个当前负责人。
4. 经 `collaborate` 或现有子 Agent 能力分派角色、Spec 修订、Ticket、前置产物、写入范围、交付与检查要求、预算、停止条件和回传位置；不向每个实现者加载整套总控流程。
5. 接收候选和原始证据，按 Ticket 的完成条件安排必要验证、独立审查与修正。`COMPLETE` 仅表示该角色完成，不能直接解除依赖。
6. 确认前置产物满足释放条件后更新依赖。已验证接口等阶段成果可供下游使用，但不自动关闭前置 Ticket；关票依据项目规则和该票交付终点。
7. 重算就绪集合并继续，直到达到本次目标或存在真实阻塞。无人可执行时区分等待产物、环境故障、依赖环和人的决定，不反复派发同一无进展任务。

参与者可在范围内直接讨论、求助与分工；各 Spec 保留自己的总控和 Ticket 归属。跨 Spec 的共享资源与集成顺序在共同记录中协调；无原子领取时由明确协调者处理重叠对象，独立工作继续。

## 4. 处理变化与整体交付

- Spec 或决定变化时保留原修订，列出受影响的 Tickets、前置产物和证据；通知相关负责人，重评相关部分，未受影响的工作继续。
- 候选、基线、配置或环境变化后核对证据是否仍适用。模型检查、源码核对、作者自查和真实运行验证分别记录，不把旧通过直接用于新对象。
- 失败按原因交回：事实与范围给调查，行为约束给设计，任务图给拆票，模型给 TLA，实现给实现者，工具故障先处理环境。达到轮次、费用或无进展阈值时调整方法，不以预算耗尽代替通过。
- 所有 Tickets 完成后仍核对 Spec 的整体验收、迁移与兼容要求。需要集成工作时明确安排；多个独立候选通过不自动证明组合通过。
- PR 按项目需要分票、分批或整体组织。依据真实平台、产物和环境状态判断终点；PR 已创建、排队或自动合并已开启，不等于实际合并，合并不等于发布。
- 工作流改进作为有明确范围的任务处理，不在普通返工中自行修改技能、放宽验收或扩大权限。

### 交付后的任务收尾

合并、发布或验收产生新结果后，在既有任务归属与授权内完成以下收尾。使用项目选定的权威记录和状态；无关联任务时不强制建票。

1. 重读关联 Tickets，回写本次产物、交付事实、检查证据和剩余工作。一个 PR 覆盖多票或一票涉及多 PR 时，分别核对实际覆盖。
2. 逐票核对完成条件与交付终点。终点、验收及必要审查均满足时，按授权转为项目的完成状态或关闭；仍待发布、验收或只完成部分工作时保持未完成。按项目规则清理应移除的标签，保留其他有效信息。
3. 按产物释放条件更新依赖及 Spec 任务目录，继续就绪工作；父 Spec 的关闭另按整体验收与项目维护约定判断。
4. 回读权威记录，确认状态、依赖和必要标签实际生效。响应丢失先查现状，只补未完成更新；无法写入时保留已发生的交付事实，列明待同步项及接续负责人或缺口，不宣称任务状态已更新。

### 交付后的资源清理

达到交付终点或明确的资源释放点后，由 `worker-land` 或现有资源负责人核对本次分支、专属 worktree 与临时材料，沿用有效清理授权执行并回读。共享资源只释放本次使用关系；仍活跃、含未保存或未交付内容、供下游使用的资源保留。无授权或暂不能清理时，交回具体 ref／路径、拟执行动作与保留原因；清理待办不改写已经完成的交付事实。

## 5. 人的介入与恢复

直接理解自然语言的裁决、暂停与改向，无须先点名技能；一般咨询不自动暂停全部工作。记录决定出处、适用范围、受影响工作与恢复条件，并核对已记录、已传递和实际生效的区别。

本次例外留在任务记录；用户明确要求长期生效的流程调整，重读后局部修订项目流程文档，保留来源和范围，不要求再调用 auto 或 steer。流程文档缺失不成为普通任务的前置门。

恢复前重读项目流程、权威记录、候选、当前归属和外部结果；超时后先查动作是否已发生，不重放上一条命令。取消请求、实际停止和既有副作用分开记录；缺少在途中断能力时停在可用安全点，保留未确认操作。

沿用仍有效的授权与决定；设计接受、阅读简报、合并许可和发布许可分别处理。真正缺少最终授权时，先把已授权工作做成具体可审查结果，再交回决定。

## 6. 汇报与交接

形成结论或交接前，把值得跨任务复用的项目事实归入已有长期上下文，保留日期、范围和证据；已有正式归属只留必要引用。写前查重并纠正受影响的旧结论，无新事实不更新；只读任务交回建议。并行产出的结论由现有记录负责人汇总，不让多个 worker 另建记忆副本。

面向人使用 `brief` 的简短白话，说明实际成果、重要设计变化、卡点与必要决定，不默认输出机器字段。未到目标时准确说明已到哪里。

接收方需要结构化记录时，使用 [结果模板](assets/work-result.template.json) 与 [work-result/v1 约定](references/work-contract.md)。`COMPLETE` 不扩大证据范围，只有到达约定终点才把整体工作标为已交付。

可用 Python 3.10+ 运行 `scripts/validate_result.py` 校验记录结构；它不证明证据真实，也不执行调度或授予权限。
