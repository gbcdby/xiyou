# 改进开发流程

减少完成有效交付所需的人类总时间，同时保持交付质量。将实际失败转成可验证的机制改进，避免仅增加说明文档或管理层级。

## 输入与边界

- 读取触发事件、相关工作对象、原始证据、现行规则、已有评估和授权范围。
- 确认本次改进对象与范围：一个项目、一个工作方法、一个工具，或一种能力组合。不要把项目特例直接推广为全局规则。
- 默认改进当前约定范围内的方法；扩大访问、降低验收、取消人工门槛或改变合并发布权限，按原有授权规则处理。
- 不以评估分数代替授权，不改写历史结果，不通过关闭必要检查提高通过率。
- 使用协作服务时核对真实事件和操作接口，不假定已有自动放量、熔断或评估能力。

## 按需资料

| 当前工作 | 读取 |
| --- | --- |
| 设计数据集、指标、实验与推广条件 | [评估与试用规则](references/evaluation.md) |
| 保存改进候选及交接 | [改进记录模板](assets/improvement.template.md) |

## 1. 从实际事件确定问题

1. 固定触发事件和涉及的版本、环境、候选及规则，取得原始失败、修复和运行事实。
2. 区分设计缺陷、实现缺陷、验证遗漏、错误上下文、工具失败、协作失效和授权不足；允许多个原因并存。
3. 找出本应发现或防止问题的环节，以及当时缺少什么。不要因结果不佳就直接换模型、增加审查轮数或追加长提示。
4. 作者拒绝一个审查意见不自动说明它是误报；先核对真实预期、代码位置和可复现条件。
5. 原因证据不足时，提出最有价值的补充调查；不要先把猜测写进通用 Skill。

## 2. 选择最小有效改进位置

| 问题性质 | 优先改进的位置 |
| --- | --- |
| 可确定地检测或防止 | 检查器、测试、类型或运行时约束 |
| 项目专属行为与失败定义 | 项目规则、验收契约或审查指南 |
| 可跨项目复用的工作方法 | 通用 Skill 的必要步骤或参考 |
| 状态、消息、所有权或操作边界 | 实际运行时及其接口 |
| 宿主工具、会话或模型能力差异 | harness 适配层与能力记录 |
| 任务不合适或缺少验证条件 | 任务拆分、上下文获取或能力路由 |

每个候选写明作用机制、预期收益、可能副作用、适用范围和回退方式。先比较少量有实质区别的改进，不无限生成方案。

修改 Skill 时使用当前环境支持的正式创建或更新流程，遵守其验证与保存要求；不改写第三方只读技能，也不绕过原版的用户触发限制。

## 3. 在改动前固定评估方法

按 [评估与试用规则](references/evaluation.md) 建立小而有代表性的集合：真实缺陷、已知正确改动、边界情境和未参与调优的留出样本。

- 预先写明主指标、不能退化的指标、统计单位和候选采用条件。
- 分开记录人的实际处理时间、等待人的时间和被打断次数；等待时间不是人工工作量。
- 同时观察真实验收、漏检、误报、有害修改建议、返工、恢复成本、审查轮次、耗时与运行成本。
- 保留原始数量、风险类别和样本不足的限制；不能用 PR 数、消息数或发现问题总数代表质量。
- 将评估标准和留出材料与可编辑的候选分开。不得在试验中修改答案、删除困难样本或降低标准来制造改善。

## 4. 运行能够比较的试验

1. 固定基线和候选版本，分别记录模型、harness、Skill、工具与环境配置。
2. 让评估者从原始任务和材料开始；不传入预期结论、已知修复或上一轮分析，避免上下文泄漏。
3. 在隔离且已有授权的环境运行。保存成功、失败、中断和未运行结果，不只保留有利样本。
4. 新组合先满足访问、工具、环境和独立性等硬条件，再比较任务类型上的质量、成本与耗时。
5. 重复审查先检查未决问题与新增变化，并用稳定问题标识去重；达到无进展或预算阈值时改变方法，不将上限当作通过条件。
6. 对改进后仍会遗漏的问题给出具体覆盖限制；不同模型多数同意不构成正确性证明。

## 5. 决定保留、有限试用或放弃

- 收益有证据、质量边界未退化且已有授权覆盖时，选择小范围试用；写明观测窗口、回退触发与负责者。
- 只能证明对已知样本有效时，保留为候选或有限试用，不宣称已泛化到所有项目。
- 漏检严重度、真实返工或人的总负担增加时，分析原因并回退或放弃；不能只优化其中一项表面指标。
- 新规则绑定明确版本。运行中的工作继续记录所采用版本；版本切换后重新评估受影响证据。
- 若没有实际放量或回退执行器，交付可执行方案与缺口；不把配置建议写成已启用。
- 若改变权限、批准门槛或已接受承诺，先完成可审查候选与评估，再提交必要决定。

## 6. 交接可复用的结果

默认给出短结果：反复发生什么、改了什么、在哪些样本上改善、代价与剩余盲区、是否需要人的决定。证据与详细样本按需展开。

接收方需要机器记录时按 [改进模板](assets/improvement.template.md) 交接，绑定基线、候选与评估集合。保留证据的原状态、对象与日期，不把静态或历史材料写成当前实测。

- **COMPLETE**：改进分析、候选和约定的试验交接已完成；说明是提出、试验、启用还是已回退。
- **PASS / FAIL**：仅表示预先定义范围内的实际评估结果，保留具体指标与条件。
- **INCONCLUSIVE**：样本不足、结果冲突或缺少真实运行依据，尚不能支持采用结论。
- **BLOCKED / NOT_RUN**：必要前提缺失或实际试验尚未运行；交出已完成部分。

维护经过验证的跨项目方法，保留项目特有规则在项目中。不要把每次事故全文追加进 Skill，也不要把一次改进完成当成持续监控已经建立。
