# 简报视图规则

## 白话与图表

默认用短句回答“有什么用、哪里变了、还差什么”。根据真实含义翻译术语，不机械替换词语：

| 内部说法 | 面向人的表达示例 |
| --- | --- |
| 当前候选缺少验证证据 | 还没找到这次修改的检查结果，暂时无法确认。 |
| 状态归属发生变化 | 原来各个客户端自己记进度，现在改由服务端统一记录。 |
| 缺少已接受架构基线 | 没找到之前确认的设计，暂时无法判断整体改了多少。 |
| 前置依赖尚未满足 | 还在等接口约定下来，后面的实现才能开始。 |
| PR 已合并，部署状态未知 | 代码已合并；是否已上线还没有确认。 |

示例中的事实必须有依据。保留必要的技术名称，并解释它对行为或取舍的影响；少用黑话不等于删除设计理由。

| 需要表达的关系 | 优先选择 |
| --- | --- |
| 单个结果、短答或简单提醒 | 一两句文字 |
| 多项工作的状态、方案取舍 | 两到三列的短表 |
| 改动前后与实际影响 | “原来／现在／影响”对照表 |
| 依赖、分支、信息流、谁负责什么 | 小型关系图或流程图 |
| 有可靠数值和范围的趋势、分布 | 标清单位和范围的数据图 |

日常简报通常只选最有用的一张图或表；确需多图时，每张只回答一个问题。图后不复述全部节点或表格行，没有可靠数值时不画完成百分比、进度条或估算趋势。

默认表格控制在两到三列，长内容拆成短句；图标签用白话并直接区分“计划”“已实现”“尚未确认”等状态。对依赖、时序和分支可用 Mermaid；最多五个节点或参与者横向排列，密集图拆小或改为纵向。平台不支持图形时用短表或文字说明，不输出难读的 ASCII 图。

少量图标可帮助定位，例如“✅ 已合并”“⏳ 还在等接口”“⚠️ 线上状态未确认”；文字必须独立表达状态，不靠颜色区分。没有需要突出的问题时不添加警告图标，不用图标装饰每一项。

## 资料新旧与权威来源

按问题选择原始证据，而非给所有来源设一个固定高低顺序：运行版本看目标环境；合并状态看代码托管平台；接受的设计看正式决定；模型检查看对应模型与配置的运行产物。

源码静态核对可以证明某路径存在，不足以证明该环境实际运行成功。文档与代码不符时显示差异及版本，不能悄悄改成更乐观的状态。

重要主张保留证据引用。另一个 Agent 的完成描述只是一项陈述，直到有足够原始证据支撑；多份摘要重复该陈述不增加可信度。

## 架构变化的两条比较线

1. **相对上次观察**：帮助用户发现最近发生的变化。
2. **相对已接受基线**：帮助用户看到多次小改动累积后的设计偏移。

两个比较对象分别记录。找不到之前确认的设计时，直说无法判断累计变化，不能写“整体没有变化”。可比较模块职责、状态由谁保存、依赖方向、公开接口和部署边界。

## 证据有效性

检查证据指向的候选、基线、契约、环境及规则版本。相关变化后，标明待重评；若项目已有可追溯的影响分析支持局部复用，展示该依据。不得仅因时间较新或结果为 PASS 就认为覆盖当前对象。

把以下内容分别呈现：已检查、未检查、检查失败、因环境受阻、证据已过期。不能把“没有报告问题”写成“没有问题”。

## 决策卡

每张卡只包含一个可独立决定的问题。先核对以下信息，面向人的默认展示压缩为“要决定什么／建议与主要代价／影响及等待后果”；会改变选择的事实和未知必须可见，其余依据按需展开：

- 要决定什么，哪条已接受承诺会变化；
- 为什么现有事实和授权不能直接决定；
- 推荐项、替代项与各自后果；
- 支持它们的证据和主要未知；
- 影响哪些工作，等待有何后果；
- 适用范围、前提和已有决定引用。

同名问题不一定是同一决定。跨项目授权、不同数据后果、前提变化与不同不可逆边界不能被摘要合并。

已有有效决定直接引用，不重复征求确认。所有实质待决事项和重要阻塞都保留短标题及影响，不能只展示前三项后隐藏其余；单纯需要 Agent 继续调查或处理的卡点不要标成“需要你决定”。

## 只读视图的停止条件

完成用户请求的理解范围即停止。缺少新的模型、运行验证或权限时，显示缺口并返回。不要领取任务、启动服务、运行 TLC、确认房间消息或更新“已接受”字段来让简报显得完整。
