# 发布与验收

按用户的实际交付位置完成工作。区分源码、构建产物、发布渠道、实际运行环境和验收结果；保留必要的恢复路径。

## 1. 确认交付契约

- 读取项目发布方式、有效 Spec/Ticket 的交付终点、目标环境、现有授权及兼容/迁移要求。目标可以是包、安装文件、站点、服务或其他产物。
- 发现真实构建与发布工具，不假设所有项目使用容器、云服务或某种语言。没有执行能力时交付可审查方案并标BLOCKED/NOT_RUN。
- 使用 [发布记录](assets/release-record.template.md) 固定 source、artifact、configuration、environment、authorization_ref 与回退前提。
- 复用有效授权，不按固定“每次发布必须问”模板重复确认；权限范围或难以撤销后果变化时按现有规则处理。

## 2. 准备和验证产物

1. 从明确来源构建或取得产物，记录版本、摘要和构建环境。取得 CI 产物时关联实际运行、源码修订、配置与目标平台，不用“latest”代替身份。多仓、多组件或多产物记录组合版本。
2. 检查实际要交付的产物与已验证产物一致。重新构建、换配置或更换平台可能使原证据不适用。
3. 以风险选择兼容、安装/启动、升级、失败与迁移验证。不要把临时环境通过泛化成生产或另一平台通过。
4. 拆开可撤销准备和难以撤销动作，在实际边界准备可审查结果。回退能力需要证据，不能只写“可一键回滚”。
5. 对数据库、外部系统和不可逆动作，明确停止点、备份/补偿依据和可恢复范围。
6. 若缺少最终授权，完成以上已授权准备后提交具体产物、目标、影响、证据和待执行动作。

## 3. 执行与核对

- 使用当前授权和项目发布机制；版本号、渠道、租户、区域和环境都要匹配目标。
- 超时或网络中断后先查询发布事实，再决定重试。稳定操作ID只在真实服务提供相应保证时使用。
- 按终点回读实际结果：分发核对渠道、产物版本／摘要和可获取性，按约定检查安装或导入；部署核对运行版本、配置、入口和关键行为。只交付包或文件时不强加服务健康检查。
- 平台状态、请求 accepted 或任务 completed 不能替代上述验收；产物已发布不自动表示用户环境已运行。
- 使用渐进发布、feature flag或内部先行仅在项目具备并适用时；不为小任务引入整套新基础设施。

## 4. 异常与恢复

按 [恢复边界](references/recovery.md) 区分失败发生在发布前、发布中还是发布后。保留实际已发生的动作，不因后续检查失败撤销事实记录。

已有恢复授权覆盖当前动作时执行并复验；没有时准备方案、保护仍可保留的结果并报告具体决定。代码revert、产物回退、配置恢复和数据补偿分别记录。

对无法撤销或结果未知的动作，不盲目重跑或声称已恢复。终止相关后续动作，核对外部真实结果。取消请求不能撤销已完成的发布或外部效果。

## 结果与交接

默认简短报告发布位置、运行状态、检查和缺口；接收方需要机器记录时按 [发布模板](assets/release-record.template.md) 交接，绑定实际来源、产物、配置和环境，保留回执、验收与恢复证据的原始状态。

明确到达published、deployed还是accepted。需要真实环境却只完成本地演示时报告差距；约定窗口内通过不保证无限期无故障。将事故和漏检的原始材料交给维护流程，不自动扩展成周期任务。

outcome仅用COMPLETE/PASS/FAIL/INCONCLUSIVE/BLOCKED/NOT_RUN；阶段COMPLETE不代替整体交付终点。
