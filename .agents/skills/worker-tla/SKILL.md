# TLA+ 设计与形式化验证

设计可检验的行为契约，运行有限范围的模型检查，并交付实现方可独立使用的约束与证据。先给出与证据相称的结论，再解释范围。使用用户的语言交流，保持性质名称与记录字段稳定。

## 职责与模式

| 模式 | 完成的工作 | 停止点 |
|---|---|---|
| `design` | 理解需求与现有边界、设计协议、建模、检查、整理交接 | 交付设计约束与验证证据；实现尚未评估 |
| `check` | 检查已有模型、分析反例、在既定需求内修正模型并重跑 | 报告已检查性质、反例和限制 |
| `align` | 用户明确要求后，只读核对源码与模型的语义对应，维护模型并重跑必要检查 | 报告对应差距或当前对应证据；缺陷交回实现方 |

- 修改范围限设计文档、TLA+/PlusCal 模型、检查配置、验证辅助文件及结果。可读取相关源码、测试和部署资料；不修改业务实现、项目测试或部署配置，不承担风格、重构或一般代码质量审查。
- 产出反例对应的回归**场景与断言**，由实现方编写和执行真实项目测试。本 Skill 不组织 TDD、应用启动或端到端测试流程。
- 后续实现由用户或外层任务安排；本技能不探测、安装、调用或编排实现工具，可独立完成形式化任务。
- 按有效 Spec/Ticket 引用交回成果；独立调用可使用等价紧凑记录。后续交付由外层负责，形式化职责完成不表示整个任务完成。
- 业务语言与工具运行环境分别处理：Python 运行附带脚本，Java 运行 TLC，二者不限制业务栈。
- 按本项目事实建立假设，不继承其他项目的事务、调度或持久化保证。常规模型修正自行推进；改变已确认业务保证时展示差异并按原需求决策流程处理。
- 无执行能力时继续完成可做的设计与分析，标记 `NOT_RUN`，不伪造结果。

## 1. 确定目标并理解系统

1. 确认项目根目录、本次需求和模式。读取相关项目规则、设计资料、源码与配置，核实真实调用方、状态所有者、持久化和外部效果边界。
2. 优先复用已有验证目录。首次可采用 `verification/<feature>/`，模型放 `model/`，证据放并列的 `runs/`，文件名随项目惯例调整。
3. 按 `assets/project-profile.template.json` 记录本项目事实、出处和未知项；没有代码时标记拟议语义与未评估项，不伪造实现依据。
4. 优先选择失败代价高、普通示例难覆盖的状态交错或故障问题。用户明确要求形式化建模时给出适当小模型；无相关风险且未明确要求时说明分流理由并交回外层任务，不自行转入开发。
5. 按问题选择检查方式。TLA+ 适合协议、状态与操作顺序；源代码的溢出、内存安全等义务应交给适合的代码级验证器或测试。本 Skill 可以记录这些未覆盖项，不能用抽象模型替代实际代码验证并宣称已完成。

## 2. 设计行为契约

使用 `assets/contract.template.md` 记录需求、设计选择、性质与假设。

- 从调用方的使用场景与可观察结果出发，写明接口输入、输出、错误／未知结果、状态转移、数据所有权及提交边界。可以使用伪代码或签名示意，不在业务源码中填实现或空壳。
- 先理解既有系统的结构与理由；新设计不能凭空改变既有所有权、部署或可靠性条件。只有存在实质架构权衡时比较少量不同方案，不对每个小改动强制多方案竞赛。
- 从业务要求推导目标，现有代码只是待核实事实。区分需求、环境假设、实现义务与开放问题。
- 给关键需求稳定编号并连接实际启用的性质；区分安全性、活性、类型约束与可达性。`TypeOK` 不能替代业务性质。
- 活性须写明调度、公平性、恢复和投递条件，不任意加强假设来消除反例。
- 分开记录必须实现的语义义务与可自由选择的技术机制。例如要求“效果提交与去重记录不可分离”，不要无依据地规定某数据库、语言或锁实现。
- 保存性质、假设、规模和排除项的基线；改变后展示差异，不能无说明地删性质、删故障或降低并发范围。

## 3. 建立最小有效模型

按 [建模规则](references/modeling.md) 明确状态、初态、动作、原子性、故障与持久化。

- 将能被并发或故障打断的步骤拆开。新设计中的原子动作是实现义务；已有实现必须有真实机制支持，不能把规格的原子性当作源码证据。
- 纳入与目标有关的重复请求、重试身份、超时未知结果、旧响应、丢失／乱序和恢复行为。
- 使用 `Init`、`Next`、`Spec` 与明确命名的性质；PlusCal 修改后先更新译文再检查。
- 确认初态非空、关键业务与故障路径可达、终止与死锁含义明确。对关键性质用隔离的错误变体或等效反例证据检查其敏感性；无法完成时逐项写明缺口，不伪造覆盖。
- 不把目标性质作为搜索约束过滤坏状态，不用随机选择或主动终止冒充穷举。错误变体独立保存，不能修改业务代码来制造演示错误。
- 普通源码对应表不构成 refinement 证明。没有相应语义与证明工作时，不宣称源代码已形式化证明。

按需参考 `assets/examples/IdempotentEffect.tla` 或 `assets/examples/LatestResult.tla`。这些案例含故障／修复配置，只用于理解或工具校验，不可直接当成本项目需求。

## 4. 执行检查与分析反例

按 [执行与证据协议](references/execution.md) 填写 `assets/verification.template.json`，使用 `scripts/run_tlc.py`。附带工具依赖 Python 3.10+、Java 11+ 和固定摘要的官方 `tla2tools.jar`。

1. 优先复用摘要一致的 jar；缺少时用 `scripts/fetch_tlc.py` 在环境权限内获取固定版本。不要绕过访问限制。
2. 每次使用新的输出目录，核对清单与真实启用的性质，保存模型／配置快照、工具摘要、实际 argv、状态与原始日志。
3. 先运行足以暴露目标风险的小配置；仅为解决具体剩余风险扩大规模。预算不足如实报告。
4. 把反例翻译成业务事件顺序，区分设计缺陷、模型错误、性质表达错误、假设冲突或实现偏离；保留旧证据。
5. 在业务目标不变的前提下修正设计或模型并重跑。源码缺陷列成交接事项，不修改业务实现，也不为获得通过而把缺陷改写成需求。

| 工具状态 | 允许表达的结论 |
|---|---|
| `PASS_WITHIN_SCOPE` | 指定模型、配置、假设与性质的检查完成，未发现违反 |
| `COUNTEREXAMPLE` | 找到性质违反或死锁，需解释其意义 |
| `INCONCLUSIVE` | 超时、中断或资源耗尽，不能得出完整通过结论 |
| `TOOL_ERROR` | 语法、配置、工具或支持范围问题 |
| `NOT_RUN` | 尚未实际运行 |

原始 runner 的 `implementation_status` 保持 `NOT_ASSESSED`；不要编辑它来表示代码已评估。

## 5. 交付可独立使用的成果

按 [交接协议](references/handoff.md)，用 `assets/handoff.template.md` 汇总：设计决策、业务性质、环境假设、实现义务、可选机制、模型与运行证据、反例回归场景、未覆盖项和返回验证条件。接收者无需掌握 TLA+ 即可理解这些约束。

- 用 `assets/report.template.md` 分开报告模型状态、模型敏感性检查、可选对应核验和交接状态；实现测试结果仅引用外部实际证据，注明提供方与版本。
- 交接完整不代表模型通过；保留阻塞问题和未满足义务，不给失败或未运行任务盖“可实现／已验证”章。
- 复杂或关键模型可交给独立上下文复核。提供原始需求、模型、配置与日志，不先灌输结论；未做独立复核时如实标记。
- 默认在交付后结束本 Skill。用户选择后续实现与通用审查工具，不自动串联。

## 6. 按需回检对应关系

仅在用户明确要求模型与实现对应核验或维护时进入 `align`，使用 `assets/implementation-map.template.md`。

- 只读核对真实源码中的原子性、状态、持久化、重试、取消、异常、部署与相关语言语义，限定于已声明性质的对应关系。
- 记录覆盖文件／符号及实际内容标识，含未提交和新增文件；没有版本控制时用相关文件快照与摘要。单独的分支或提交名不能代表当前全部内容。
- 区分对应关系未变化、模型过时、实现违约和检查受阻；模型更新后仍可能暴露实现缺陷。保持业务性质，不为适应 bug 弱化要求。
- 将对应核验状态与 TLC 状态分开。只有对应关系核对完成且所需检查完成，才推进对应基线；有缺口、反例、阻塞或未完成运行时保留旧基线并记录本次评估目标。
- 报告缺口及需要实现方提供的证据，不编写修复代码或真实测试。语义变化后重新检查受影响范围，不拿旧模型通过支持新源码。

用户明确要求模型 CI 时可复用固定执行器与清单接入既有质量流程；不顺带组织实现测试、部署或周期任务。组件模型分别通过不能自动推出组合系统正确，组合性质需另行建模或论证。
