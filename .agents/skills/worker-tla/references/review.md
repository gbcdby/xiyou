## 限定复核对象

本文件负责设计与形式化验证的证据复核。通用代码质量、编码规范、TDD、真实项目测试编写和业务代码修复由实现方负责。`align` 的源码读取只用于核对已声明的模型语义。

向独立复核者提供原始资料，不用“已正确”“已修复”等作者结论替代判断：

- 原始需求、已确认规则、任务模式和功能边界。
- 性质、环境假设、排除项及开放问题。
- 实际检查的模型、配置、依赖、输入摘要与原始运行日志。
- 反例、可达性或错误变体证据；区分预期失败探针与交付配置。
- 仅在 `align` 时附实际源码快照、覆盖文件／符号及实现方提供的测试证据。

独立上下文有助于发现遗漏，不构成数学证明。没有独立复核者时先从原始要求自查，并记录独立复核 `NOT_RUN`。

## 检查模型与范围

1. 对照需求检查遗漏的业务性质、参与者、交错、故障和恢复路径。
2. 核对配置真实启用的性质；只在注释或模型中定义而未启用不算检查。
3. 核对原子步骤与抽象层次。新设计原子动作是实现义务；已有源码的原子性必须有独立依据。
4. 查明单写者、事务、可靠传输、最终恢复和公平性等假设的来源。
5. 确认初态非空，关键业务与故障路径有可达见证，性质没有因前提永不成立而空洞通过。
6. 对关键性质审查错误变体或等效敏感性证据，记录具体触发的性质；语法错误、工具失败不能算检测到目标业务错误。
7. 检查范围缩小、状态／动作约束、归约、覆写或关闭死锁检查是否隐藏风险。
8. 核对完整运行状态、队列与原始日志；不只搜索成功字符串，不复用修改前的结果。
9. 多个模型分别通过时，检查接口假设是否兼容；缺少组合论证时只报告组件结论。

## 解释反例

先转成业务事件顺序，指出首次违反的性质、相关状态和环境条件。

| 分类 | 判据 | 本 Skill 的处理 |
|---|---|---|
| 设计缺陷 | 允许的行为违反已确认目标 | 修正设计与模型，保留性质并重跑 |
| 模型错误 | 模型误写状态、动作或抽象边界 | 依据设计修正，说明为何没有隐藏真实行为 |
| 性质表达错误 | 公式偏离原业务要求 | 修正表达，保留需求关联与差异 |
| 假设冲突 | 环境条件与业务保证无法兼容 | 揭示冲突，记录需决策的条件 |
| 抽象额外行为 | 过粗抽象产生无法对应目标的行为 | 用事实细化，不能仅说“现实不会这样” |
| 实现偏离 | 实际机制不满足设计义务 | 只读记录证据与交接事项，保留缺陷，不改源码 |

- 常规模型修正与重跑沿用任务授权，不增加逐次确认。
- 若实质改变已确认业务目标，展示差异并按原需求决策流程处理。
- 删性质、缩小规模、排除故障或增强可靠性均须保留前后差异与理由。
- 活性反例须说明循环或无限停滞条件，不能只截有限前缀当普通错误状态。
- 未解决的真实反例必须保留；交接完成不表示反例已消除。

## 描述回归场景

只为能够对应真实业务的反例生成回归**规格**，不编写或运行真实项目测试：

1. 指定参与者、初始状态、输入和要满足的前提。
2. 写出关键操作顺序、可打断点、故障／恢复位置。
3. 指明应控制的调度或依赖行为，以及能观察的业务结果。
4. 绑定需求 ID、性质、原始反例证据和独立于实现算法的断言。
5. 说明预期错误行为与修复后应有行为，实际测试结果保持 `NOT_RUN`，直到实现方提供对应证据。
6. 不能直接重放时解释抽象差异和需要的额外映射，不声称可以跨语言自动回放任意 TLC 轨迹。

可建议屏障、可控时钟或故障注入等能力，但接口改动与测试实施留给实现方。不要通过总成功的 mock 删除待检验的失败窗口。

## 按需核验源码对应

仅在用户明确要求实现与模型对应核验／维护时执行 `align`，使用对应模板。

- 固定本次评估的真实内容：已提交、暂存、未暂存、相关新增／删除文件和必要配置。单独 `HEAD` 或提交间 diff 不能覆盖当前工作区。
- 无版本控制时记录相关文件内容摘要与安全快照；不强制建立版本库。不要把敏感配置复制到证据目录，只记录必要语义与来源。
- 记录被覆盖文件、稳定符号、关键状态写入者及外部依赖；重命名、移动或新增写入者可能使旧覆盖表失效。
- 逐项核对模型动作在代码中的拆分、事务范围、锁／条件写入、效果身份、提交／确认、取消／异常和崩溃恢复。
- 检查与当前性质有关的数值、内存可见性、时钟、序列化、部署与依赖语义差异。不把检查扩大成全仓库风格或质量审查。
- 读取现有测试和实现方给出的测试记录作为补充，注明代码版本、命令、结果及提供方；源码里有测试不表示已执行。
- 发现不对应行为时说明代码依据、受影响性质与模型反例是否可重放，交给实现方处理；不修改业务代码、项目测试或生产配置。

更新模型可以描述当前实际行为并揭示违反，但不能把错误行为改成新的正确要求。必要时保留目标设计模型与描述当前实现的模型，注明各自含义。

## 维护对应基线

区分“最近检查过哪些源码”与“最近有完整对应证据的基线”。失败或阻塞也应记录本次评估目标，但不能冒充新的有效基线。

| 分类 | 含义 | 后续 |
|---|---|---|
| `IN_SYNC` | 已核对语义仍与模型一致 | 按变化影响执行必要检查 |
| `MODEL_DRIFT` | 模型或覆盖记录未反映当前相关行为 | 更新模型／对应记录并检查 |
| `IMPLEMENTATION_GAP` | 当前源码不满足既定设计义务／性质 | 保留问题，交给实现方 |
| `BLOCKED` | 缺少源码、依赖语义或执行能力 | 明确缺失证据与可继续部分 |

这些分类可同时出现，例如更新模型后发现实现缺陷；不要强行互斥。`model_updated` 单独记录，模型更新不等于问题解决。

仅当相关语义已核对、对应缺口已解决、必要模型检查完成且无未解决反例，才推进有效对应基线。纯改名可说明无需重跑的具体理由，但仍需核对覆盖与内容对应。有限模型通过本身不能推进源码对应基线。

需求、性质、并发参与方、事务／持久化边界、消息保证、运行时或部署拓扑变化均需评估证据失效；无关展示变更无需扩大检查。

## 分别报告结论

| 层次 | 状态或内容 | 不可混淆的边界 |
|---|---|---|
| 模型检查 | runner 原始状态、范围、性质与证据 | 有限检查不推出任意规模或源码正确 |
| 敏感性检查 | `DEMONSTRATED / PARTIAL / NOT_RUN`，逐性质证据 | 错误变体被发现不表示遗漏全部排除 |
| 源码对应 | `NOT_ASSESSED / PARTIAL / GAPS_FOUND / ASSESSED_WITHIN_SCOPE` | 工程对应核验不是 refinement 证明 |
| 独立模型复核 | `NOT_RUN / ISSUES_FOUND / REVIEWED` | 不能替代运行证据 |
| 交接材料 | `COMPLETE / PARTIAL` 与阻塞事项 | 材料完整不代表已通过或实现完成 |

真实实现测试由实现方负责；报告只引用已有可核验记录，不把计划或预期写成实测。保持 runner 中 `implementation_status: NOT_ASSESSED`，对应核验放单独记录。

## 确定完成条件

- 已完成请求的 `design`、`check` 或 `align`；未授权的后续实施没有被纳入本 Skill。
- 性质、假设、范围与实际状态可追溯，未检查项逐项说明。
- 反例已解释；设计／模型修正已重跑，未解决问题仍可见。
- 交接包含实现义务、自由机制、回归场景和返回条件；没有代码时明确未评估。
- 有充分证据时停止可选扩大检查，后续工作由用户或外层任务选择。
