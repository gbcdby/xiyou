适配信息用于理解设计、整理交接，以及用户明确请求的只读模型与源码对应核验。本协议不授权修改业务代码、项目测试或测试钩子，不组织 TDD、应用启动或 E2E，也不调用后续实现或审查 skills。

## 发现项目事实

1. 阅读当前任务、项目级开发约定、已有架构文档和相关变更，确定 `design`、`check` 或用户明确要求的 `align` 模式。
2. 优先复用已有模型验证目录与工具版本；发现现有测试框架和任务入口时仅记录供交接，不为使用本 Skill 改造整个项目。
3. 用 `rg --files` 或等价文件索引查找构建清单、锁文件、测试入口、数据库迁移和部署配置，再读取相关文件。
4. 先定位行为边界：参与者、共享资源、持久化、外部副作用、重试与取消、终态。
5. 有代码时从相关源码、配置及版本对应的官方资料理解运行语义；文件扩展名或接口名称不能证明原子性。无代码的设计任务记录拟议语义、实现义务和未知项，不虚构机制依据。
6. 区分开发、测试和生产环境的保证。通过已有资料理解差异，不自行启动应用、访问线上系统或执行真实项目测试；模型检查使用适合本任务的本地资料。
7. 记录尚未确认的语义；可先检查不依赖这些语义的部分。阅读源码辅助设计不等于已完成 `align`，不能据此宣布整个实现已符合模型。

## 建立适配记录

将与当前模式有关的信息写进功能契约或对应记录，沿用项目格式即可，不为填满表格扩大任务范围。这些字段是设计与交接记录，不代表执行脚本会自动读取或执行其中的命令。

| 字段 | 最少记录什么 |
|---|---|
| `mode` | `design`、`check` 或用户明确要求的 `align` |
| `project_root` | 项目根目录；记录中使用相对路径，运行时再解析 |
| `feature_boundary` | 当前功能、参与组件、外部接口、相关源文件 |
| `source_revision` | 被分析内容的基准版本、相关 WIP 与新增文件；必要时以文件快照和内容摘要标识 |
| `runtime` | 语言、运行时版本及线程／进程／协程／事件循环等并发方式；区分观察到的事实与拟议条件 |
| `state_storage` | 内存、数据库、缓存、文件、队列及所需持久化／一致性保证；注明依据或待实现状态 |
| `atomicity` | 设计要求的不可分割边界；已有机制的真实依据与尚未满足的义务分别记录 |
| `environment` | 外部服务、消息语义、网络与故障假设 |
| `numeric_time_semantics` | 数值范围、溢出、精度、时钟及超时定义 |
| `model_mapping` | 拟议的对应条件；仅在 `align` 中记录实际核对的文件、符号、性质及缺口 |
| `test_interface` | 已有观察／控制接口和缺失能力，供实现方选择或补充；本 Skill 不添加或调用这些接口 |
| `commands` | 从项目发现的构建／测试命令，以 `argv` 和 `cwd` 记录为交接信息，不默认执行 |
| `evidence` | 模型运行证据、可选对应核验记录、实现方提供的真实测试结果及各自内容版本 |
| `unknowns` | 未确认的依赖、缺少的实现方证据、无法对应的操作及范围外义务 |

源版本必须标识实际分析的内容：Git commit 只标识基准，不包含 WIP 或新增文件。记录相关文件清单及实际内容摘要；无 Git 时保存相关内容快照及摘要。没有实现代码时标为“待实现／未评估”，仅标识设计与模型版本，不捏造源码版本。

为已发现、需要交接的命令记录 `id`、`argv`、`cwd`、已知的超时和适用环境，并注明来源；未发现入口时写明缺口。路径相对项目根目录，不存放访问令牌或个人机器的绝对路径。

```json
{
  "id": "feature-regression",
  "argv": ["<project-test-command>", "<feature-test-selector>"],
  "cwd": ".",
  "timeout_seconds": 120,
  "environment": "local-test"
}
```

这个片段只是交接格式示意，不能直接执行；命令与超时必须替换为有依据的值，未知时明确标记。测试命令的存在不代表执行授权，也不代表该测试已经运行或覆盖某项性质。

真实项目测试由实现方编写和执行。引用其结果时记录提供方、命令、环境、运行证据和源码内容版本；版本不符或证据不全时标记缺口，不作为当前实现已通过的依据。

TLC 执行使用本 Skill 的 manifest 契约；语言、数据库和测试工具的适配记录不改变它的通过标准。不得把实现方测试的退出码或模型对应记录写成 TLC 检查结果。

## 核对跨语言语义

按实际风险选择核对项，保留必要差异。不要将整套语言实现细节放入每一个模型。

| 语义 | 需要建立的对应 |
|---|---|
| 并发与调度 | 哪些步骤可交错？是否存在多个进程、实例或设备？异步等待是否让出执行权？ |
| 共享内存 | 数据竞争、原子变量、内存可见性和重排是否影响性质？模型是否只假设顺序一致性？ |
| 数值 | 数学整数是否对应有限宽整数、浮点或十进制定点？溢出、舍入和比较是否影响性质？ |
| 集合与身份 | 键是否稳定？是否有大小写、编码、序列化或相等判断差异？ |
| 时间 | 使用单调计时还是日历时间？期限边界、时钟偏差和租约续期是否影响正确性？ |
| 异常与取消 | 抛出异常、任务取消、清理和回滚发生在哪些步骤？外部效果能否撤回？ |
| 持久化 | 写入、提交、确认和崩溃恢复之间的可观察顺序是什么？ |
| 跨端／跨服务 | 是否存在消息版本差异、重试代理、缓存或客户端旧状态？ |

- 不因某语言具有内存安全、全局锁或单线程执行，就推断业务操作不可交错。
- 不因函数名称是 `atomic`、`transaction` 或 `synchronized`，就推断它覆盖所有参与方和外部副作用。
- 仅在目标性质依赖时引入弱内存、浮点或复杂时间模型；否则明确省略理由，将所需的代码级验证或测试列为实现方的交接义务。
- 不把“模型使用整数／集合”直接解释成实现必须使用某一种语言或容器。
- 遇到特定语言或数据库语义不确定时，查阅该运行时／数据库的官方文档，保留版本和依据。

## 记录实现方需要的观察与控制能力

把反例翻译为实现方能够理解的操作序列、前置条件与断言。只读查找已有接口；缺少必要能力时写入交接，不生成业务框架，不新增或修改测试钩子、夹具和项目测试。

| 需要的能力 | 可记录的现有接口或交接条件 |
|---|---|
| 初始化 | 测试夹具、内存状态、隔离数据库或容器 |
| 执行动作 | 领域函数、服务方法、消息处理器或测试 HTTP 客户端 |
| 控制交错 | 屏障、显式调度器、测试钩子或可控执行器 |
| 注入故障 | 假时钟、可控网络／存储适配器、进程终止与恢复夹具 |
| 观察状态 | 测试只读查询、事件日志、公开结果或必要的内部断言 |
| 清理 | 实现方测试需要的隔离边界、资源释放和证据保留条件 |

- 区分模型中的抽象步骤与已知真实操作；尚未确认可重放的反例标为待核对，不能宣布已在产品中复现。
- 交接应指出需要保留哪些事务、锁和持久化语义；替身若消除了关键竞争或失败，就不能支持相应结论。
- 对竞争问题说明必须控制的执行顺序，不把固定休眠或概率性重试列为充分的正确性依据。
- 只提供场景、前置条件、观测点和断言；新增接口、测试实现及执行方式由实现方决定。
- 若只有黑盒接口，说明哪些内部步骤无法观察或控制；外部测试结果不等于全行为对应证明。

## 连接不同项目形态

| 项目形态 | 设计与模型优先关注 | 实现方可提供的补充证据 |
|---|---|---|
| 单进程领域逻辑 | 状态不变式、异常、取消、可重入调用 | 领域测试、边界与性质测试 |
| 多线程／多进程服务 | 读写交错、锁范围、竞争、内存可见性 | 可控并发测试、运行时相关工具 |
| 数据库驱动服务 | 事务隔离、唯一性、提交与重试、连接失败 | 使用相应数据库语义的集成测试 |
| 分布式／事件驱动系统 | 投递与确认、幂等、部分失败、恢复和顺序 | 消息／故障注入、隔离多实例测试 |
| 前端／移动端异步流程 | 过期响应、取消、重复操作、离线与重连 | 假时钟、可控响应顺序、状态机测试 |
| 带 AI 决策的业务系统 | 有限动作集合、授权、重试、超时、外部副作用 | 用可控决策替身检查流程约束 |

如果业务包含语言模型，把目标范围限定为协议和工具调用约束；不能从有限状态模型推出回答质量、事实正确性或任意自然语言安全性。

## 按模式使用记录

- `design`：建立设计契约、性质和模型，交付实现义务与证据。已有代码用于理解边界；尚无代码时写拟议条件，实现状态保持未评估，不把设计要求当成已存在机制。
- `check`：核对已有模型、配置、性质及相关假设，执行模型检查并分析反例。适配信息不完整时说明对结论的影响，不自动扩展为源码核验或项目测试。
- `align`：仅在用户明确请求时，只读核对已声明性质与真实源码的对应，必要时维护模型并重跑检查；业务缺陷和所需测试交回实现方，不自行修复或执行。
- 对模型、配置、契约、关键实现或依赖语义的变化，记录哪些证据失效。未获准进入 `align` 时，把需要重新核对的范围列为返回验证条件。
- 将 TLC 状态、模型与源码对应状态、实现方测试结果分别记录。内容版本一致也不自动证明语义对应；缺口、阻塞、反例或所需检查未完成时不推进对应基线。
- 用户明确要求模型 CI 时，可把固定 TLC runner、manifest 与资源预算接入既有检查入口；只读取本次新结果，不以旧的 `PASS_WITHIN_SCOPE` 报告作为通过依据。
- 模型 CI 不延伸为真实测试、应用运行、部署或周期任务。外层任务另有已授权的实现工作时，交回调用者处理，不在本 Skill 内扩大职责。
