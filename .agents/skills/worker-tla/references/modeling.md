## 确定验证问题

1. 先从需求、已确认的业务规则或协议中提取性质，再读取实现。不要把现有代码的行为自动当成需求。
2. 为每项要求分配稳定编号，例如 `R1`；记录原文来源、允许的例外、对应性质名称和验证范围。
3. 将信息分为 `requirement`、`assumption`、`implementation_fact`、`open_question`。未核实的实现保证不能升级为事实。
4. 明确本次模式：新设计、现有设计审查、已有模型检查，或模型与实现对应审查。
5. 选择一个有实际风险的行为边界。不要为样式、静态内容或无相关风险的简单修改建立大模型。
6. 需求不完整时，先完成不依赖该歧义的部分；仅在不同答案会改变业务性质或关键环境假设时提出问题。

建议采用如下性质清单；名称应描述业务保证，而不是实现方法。

| 字段 | 用途 |
|---|---|
| `id` | 需求编号，供模型、实现位置和测试共同引用 |
| `statement` | 精确的业务规则及量词范围 |
| `kind` | `invariant`、`temporal` 或人工审查项 |
| `operator` | 对应的 TLA+ 操作符名称 |
| `assumptions` | 该规则依赖的环境条件 |
| `coverage` | 哪些模型配置和实现测试覆盖该规则 |

## 选择状态与原子步骤

- 描述足以判断目标性质的状态；从状态可观察性和行为差异选择抽象，而不是逐行翻译代码。
- 给每个变量确定有限取值域、初始条件和更新责任。单独检查 `TypeOK`，但不要让它代替业务性质。
- 将 `Init`、各动作、`Next` 和待检查性质分开，使审查者能看清行为与要求。
- 为每个动作明确前置条件、更新变量和 `UNCHANGED` 变量，避免遗漏变量造成不受控取值。
- 高层目标可以用原子操作表达。若声称覆盖实际实现，就必须拆开真实可交错的步骤，或提供事务、线性化点、锁／条件更新等对应依据。
- 区分“模型要求此操作原子化”和“实现已保证原子性”。前者是待落实约束，不能作为后者的证据。
- 对读后写、检查后执行、跨 `await`、跨服务操作和崩溃边界，主动检查是否需要增加中间状态。
- 明确锁的范围、持有者、释放条件及故障后的行为。名字叫“锁”或“事务”并不足以证明覆盖了所需操作。
- 若省略缓存、工作线程、传输队列或持久化步骤，说明省略为何不影响正在检查的性质。
- 若需要比较抽象模型与细化模型，显式给出状态映射与待检查关系；普通代码对应表不等于完成形式化细化证明。

## 描述环境与故障

按当前系统的真实边界选择故障，逐项记录 `included`、`excluded` 或 `unknown`；无需把所有故障都塞进一个模型。

| 边界 | 需要核对的问题 |
|---|---|
| 请求 | 是否可并发、取消、重复、延迟或重排？重试是否保留同一业务身份？ |
| 消息 | 是否可丢失、重复或乱序？确认与效果之间是否存在失败窗口？ |
| 进程 | 可以在哪些步骤崩溃？重启保留什么？是否可能有多个实例？ |
| 存储 | 原子性、隔离级别、唯一约束、持久化和读可见性由什么提供？ |
| 时间 | 超时代表失败还是结果未知？计时源是否单调？租约可能重叠吗？ |
| 外部系统 | 调用副作用是否可查询、撤销或去重？本地事务是否覆盖不了它？ |

- 将外部返回结果建模为适当的非确定选择，保留实际可能的成功、失败和未知结果。
- 将时间推进表示为显式状态与动作；不要让 `JavaTime` 等真实时钟或工具运行状态决定 `Init`／`Next`，否则可达图不再只由模型状态决定。
- 区分请求身份、业务效果身份和重试次数。使用新的请求编号不能自动阻止同一业务效果重复发生。
- 区分易失状态与持久状态；崩溃动作只清除现实中会丢失的部分。
- 不以“最终都成功”简化重试，也不默认消息恰好投递一次。若系统契约确有保证，应记录其来源。
- 在多组件系统中明确哪些环境行为受当前组件控制；禁止把外部参与方的正确行为默认为实现事实。

## 分别表达安全性与活性

- 安全性表达禁止出现的坏行为，例如资源不超卖、结果不重复、失效凭据不被接受。
- 活性表达在明确假设下最终出现的结果，例如已接受任务最终完成或报告失败。
- “最多一次”不蕴含“至少一次”，“没有重复”不蕴含“请求会结束”。分别命名、配置和报告。
- 对活性使用包含相关时序和公平性条件的完整规格，保留所有环境假设。
- 只在现实调度或协议能支撑时添加公平性。弱公平性针对持续可执行的动作；强公平性涉及反复可执行的动作。两者都不是工具自动赋予真实系统的保证。
- 若允许永久故障、无限丢包或永久不调度，说明为何仍要求最终进展；否则将恢复、投递或调度条件写明。
- 不为了消除活性反例而随意加强公平性。先判断反例是否指出真实饥饿或遗漏的环境条件。
- 区分允许状态不变的 stuttering 与 TLC 的死锁检查。规格允许 stuttering，不代表没有可执行动作时 TLC 就不报告死锁。
- 对合法终态，可用仅在终态启用的显式自循环表示完成；不要添加任何状态都能执行的自循环来掩盖意外死锁。
- 若关闭死锁检查，记录业务原因和替代检查。对需要进展的系统，不能将关闭死锁检查视为解决问题。

## 选择有限检查范围

1. 先选择能产生目标交错行为的小配置；例如至少容纳两个参与者和重复请求，而不是只运行无竞争配置。
2. 记录参与者、消息、请求、资源、计数器和时间抽象的范围；参数值需要足以暴露具体风险。
3. 将规模作为配置。分别运行必要的小配置和扩展配置，不宣称一个小模型通过就覆盖任意规模。
4. 防止无界计数器、不断增长的历史和无界时间使状态空间无限。改动抽象时说明哪些行为被合并以及性质为何仍有意义。
5. 区分系统固有上限和为了检查而设置的上限。人为截断必须在结果中可见，并检查边界是否阻止了关键行为。
6. 不把待验证性质本身或等价条件放进 `CONSTRAINT`／`ACTION_CONSTRAINT` 来筛掉反例。
7. 真正的协议守卫可以限制动作，但须能对应到设计／实现；工具的搜索裁剪不能冒充协议保证。
8. 默认不使用 `VIEW`、自定义 Java 覆写或未经审查的归约。需要时先证明其不会隐藏目标错误，并记录到验证范围。
9. 活性检查默认不使用对称归约；启用任何优化前核对具体工具版本的限制以及性质是否被保留。
10. 超时、内存不足和模拟没有发现错误都不是完整模型检查通过。减少范围后的新运行应作为新的、有明确范围的结果。

## 检查空洞通过

- 确认 `Init` 至少生成一个状态。初始状态为空时不得接受“无错误”为业务验证结果。
- 确认关键业务步骤有可达见证；例如确实发生过成功、取消、重试或恢复，而不是全部被前置条件堵住。
- 检查性质中的前提是否从不成立、集合是否为空、参与者是否被遗漏，以及终态是否被错误提前进入。
- 使用动作覆盖、独立可达性配置或可复现见证补充审查；“有很多状态”本身不能证明目标场景覆盖完整。
- 若通过检查目标状态的否定来寻找可达见证，将该运行标为预期反例探针，不能混入交付通过记录。
- 对关键性质，在隔离的模型副本中引入已知设计错误，或提供等效的目标反例证据；确认相应性质确实能捕捉错误。不能完成时逐项记录敏感性检查缺口。
- 变异检查用于发现规格失效，不证明所有遗漏都已排除。不要修改真实业务代码来制造演示错误。

## 使用 PlusCal 与模块

- 适合过程式算法时可以使用 PlusCal；需要丰富组合和抽象时直接使用 TLA+。不规定一种写法适用于所有系统。
- PlusCal 源码变化后重新翻译，保留生成关系和工具版本，避免检查陈旧译文；不要直接修改生成区域后声称它仍对应源码。
- 列出自定义模块和外部依赖，确保执行快照包含实际检查的版本。未解析或未记录的依赖应使证据不完整。
- 使用标准模块时记录工具包版本和哈希；不要把机器上的偶然搜索路径作为可复现依赖。
- 将多个子模型的依赖、共享状态和接口假设列出来。局部检查通过不自动推出整个系统满足相同性质。

## 提交模型前复核

- 需求与性质一一对应；遗漏项明确标记为未检查。
- 配置确实启用了计划检查的不变式和时序性质。
- 原子性、故障、时间和公平性假设有可审查依据。
- 有非空初始状态以及目标场景的可达性证据。
- 规模、裁剪和归约对结论的影响明确。
- 模型与配置变化后重新运行，结论绑定到本次快照。
