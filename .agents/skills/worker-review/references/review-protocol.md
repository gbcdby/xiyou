# 审查协议

## 构造完整审查对象

先明确审查对象和有效需求。首次设计可直接审查完整方案，无需历史差异。代码或已有产物变更再从用户目标、PR 或工作契约取得基线与目标，记录实际 base_id、head_id、merge_base_id；集成候选另记真实身份。不要混淆三点 diff 的 merge-base 与目标分支 tip。

在 Git 项目可先执行以下只读命令；根据真实引用补全比较命令，不原样执行尖括号占位符：

```bash
git rev-parse --verify HEAD
git status --porcelain=v1 --untracked-files=all
git diff --cached --name-status
git diff --name-status
git ls-files --others --exclude-standard
```

已提交变更先核实引用，再读取 `git diff <merge-base> <head>` 与相关日志。审查当前工作树时，范围是已提交变化、staged、unstaged、untracked 以及删除的并集；以最终实际文件内容审查，避免把同一问题按多个 diff 重复报告。未跟踪文件要显式读取；常规 `git diff` 不会包含它们。

记录实际内容快照或计算得到的摘要，包含相关路径、内容、删除与必要文件模式。不要编造 worktree_digest，不把 HEAD 当作脏工作树的完整身份。对秘密文件只记录必要存在性和影响，不输出内容。非 Git 项目用明确的旧/新产物和完整清单替代。

引用不存在、候选持续变化或需要的文件无法访问时，说明已读范围与缺口；不能把空 diff 当作质量通过。没有任何可审材料或尚未开始时返回 NOT_RUN；首次设计没有旧版不属于无材料。

## 两条审查轴

| 轴 | 依据 | 核对内容 | 输出限制 |
| --- | --- | --- | --- |
| requirements | 当前确认需求、验收、设计约束、适用契约 | 正常路径、故障、并发、兼容、恢复、迁移及边界是否满足目标 | 缺少需求时标未覆盖；不能声称需求满足 |
| standards | 项目指令、已有明确约定、语言或框架约束 | 架构边界、公共接口、持久化、可维护性与可操作性 | 不把个人风格、臆造规范或工具已可靠强制的细节当阻断 |

需求和标准分别出结论；同一根因可互相引用，但不要把不同问题并成一个总评分。每项判断必须联系真实触发条件、代码或文档位置以及可观察影响。

实现说明只提供线索。独立获取相关代码、契约、消费者与验证材料，尤其注意接口改动后的新增调用方、测试和适配器。出现关键假设变化时重新检查设计依据；不要把猜测写成已复现缺陷。

## Findings 与稳定身份

按 `R-<work_id>-001` 等分配一次性稳定 ID；改措辞、行号或候选版本不换 ID。相同根因和修复边界可合并；不同触发条件不能仅因标题相似而合并。

每项包含：id、axis、severity、blocking、status、subject_id、location、rule_or_acceptance、trigger、impact、evidence_ids、recommended_action。没有足够证据时标为待核验问题并说明能消除不确定性的最小检查。

优先采用项目严重度。没有约定时按影响与发生条件解释严重度；是否阻断必须单独明确，不以夸张措辞替代证据。

| Finding 状态 | 语义 |
| --- | --- |
| OPEN | 已确认且尚未处理的问题 |
| FIX_REPORTED | 作者称已修复，审查者尚未验证 |
| VERIFIED | 已对新候选检查修复及必要影响范围 |
| ACCEPTED_RISK | 具有相应决策权的主体已接受，记录授权与范围 |
| DISMISSED | 新证据表明问题不成立，保留原因与证据 |

作者不能通过修改状态替代审查者核对。旧报告中的修复结论也不自动适用于新候选。

## 复审与收敛

1. 固定上一轮审查对象和新候选，核对基线、契约、环境是否变化。
2. 审查两次候选之间的变更、相关依赖与消费者；处理旧问题同时寻找新引入问题。
3. 用最新完整变更清单对照累计已审范围；任何新增路径、旧时未读内容或受影响边界都补审。
4. 只有明确仍适用的检查才保留，并注明原 subject_id 与适用理由；不能把旧证据标签改成新候选。
5. 最终检查没有覆盖缺口后才给出整体结论；基线或契约大幅变化时重建审查范围。

默认收敛阈值：两轮修正复审后，若同类阻断问题重复或关键未决范围不减，停止逐项补丁循环，把最小反例与设计缺口交回负责环节；返回 FAIL 或 INCONCLUSIVE。必要时在已有授权内设定新的明确范围与预算再继续。预算耗尽、票数多数或“已审很多轮”都不是 PASS 的依据。

## 独立性

常规完整审查默认分配两个新上下文，各自读取同一固定候选及本轴依据，首轮不读取作者推理或另一轴报告。汇总时保留各轴原结论与来源；同一根因可关联去重，不能让一轴通过掩盖另一轴失败或未执行。单轴委派直接完成本轴，不继续拆分审查者。

目标明确、影响局部且低风险的简单变更，项目允许时默认一位独立审查者分别检查两轴；风险看实际影响，不看行数。能力、预算受限时也可如此安排，披露实际方式与限制。无独立审查者时可做 self_check，但不能满足独立审查门槛；不同模型并非必要条件。
