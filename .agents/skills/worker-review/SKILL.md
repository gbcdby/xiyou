# 独立审查变更

对真实候选进行有范围的审查，把需求结论、标准结论和未决问题分别交付。已有授权足够时直接推进，只有实质决策缺口才升级。

## 1. 固定审查契约

- 读取用户目标、项目指令、有效 Spec、相关 Ticket 及验收条件、候选与既有审查结果；任务清单勾选不能替代对候选的审查。
- 沿用 work_id，说明本次审查范围、必须覆盖的轴和是否要求独立审查。
- 从当前任务或可信元数据取得比较点；不明确时先检查可确定范围，再提出最小缺口。
- 记录 subject.kind 与真实 subject.id；按需补 base_id、head_id、merge_base_id、contract_id、environment_id、worktree_digest。
- 区分基线分支 tip、共同祖先、feature head 与实际集成候选；不要拿一份审查替代所有对象。
- 读取 [审查协议](references/review-protocol.md) 构造完整范围与 findings 记录。

## 2. 收集完整候选

设计审查以真实版本的 Spec、相关决定和验收为对象；首次设计没有历史差异也可按约定范围审查。以下代码差异规则仅用于有相应变更的候选。

- 提交审查读取实际比较差异和受影响上下文；先验证引用有效。
- WIP 审查合并考虑已提交变化、staged、unstaged、untracked、新增与删除。
- 显式读取未跟踪文件；常规 git diff 不包含它们。不要把 HEAD 当作脏工作树的完整身份。
- 使用真实内容摘要或可重建快照；仅有文件名清单不能充当稳定身份，不能固定内容时明确证据缺口。
- 阅读相关消费者、接口、测试、适配器和配置，关注变化所影响的契约；不无目的通读全仓库。
- 引用无效、空差异或读取失败时说明原因；“没看到代码”不是通过证据。
- 不覆盖用户改动，不通过自动提交、stash、reset 或 checkout 来清理审查对象。

## 3. 保持独立性

- 完整的常规功能、接口或架构审查，默认两个相互独立的新上下文分别负责需求与标准，并行可用时并行；已指定单轴的委派不再递归拆分。
- 两轴绑定同一候选，提供契约、差异和原始材料，不继承作者推理、期待答案或对方首轮结论；完成后再汇总。
- 每轴注明实际审查者及 independent 或 self_check；作者自查不能满足独立审查要求。可使用同一模型，不以代理数量或投票证明可靠性。
- 目标明确、影响局部且低风险的简单变更，项目允许时默认一位独立审查者分开完成两轴；不按行数判定风险。能力或预算受限时也可采用此方式并披露限制；缺所需独立性时如实保留缺口，不额外制造人工批准。
- 接入已有审查技能时核实其实际版本与范围；不得绕过 user-invoked 或其他调用限制。

## 4. 分轴审查

### 需求轴

- 逐项核对当前验收、设计不变量和真实使用路径，标明满足、违约或未知。
- 检查必要的失败、并发、重试、恢复、迁移与兼容路径；按本次风险选取。
- API 或异步约定改变时查找全部相关消费者，包含新测试和适配器；文本合并成功不代表兼容。
- 需求缺失或冲突时明确未覆盖，不用代码现状替需求作结论。

### 标准轴

- 使用项目实际规定、已有架构边界和适用语言约束；不要制造个人风格门禁。
- 关注会影响维护、运行或集成的真实问题，说明触发条件与影响。
- 已被可靠工具检查覆盖的机械细节引用原始结果即可；不重复制造无意义 findings。
- 区分静态疑点、已复现行为和验证缺口；不把推测写成已确认缺陷。

不要把两轴混成一个评分，也不要把某一轴未执行隐藏在总 PASS 中。

## 5. 输出可处理的问题

- 给每个根因分配稳定 finding ID；后续改措辞、行号或版本时沿用。
- 记录 axis、severity、blocking、status、subject_id、位置、依据、触发条件、影响、证据与建议动作。
- 采用项目严重度；没有时按实际影响解释。只有有依据的阻断问题才阻止当前阶段通过。
- 合并同一根因的重复发现，保留独立触发条件；不要为了减少数量合并不同问题。
- 标准或需求暂缺时提出最小核验动作；不要虚构权威、运行结果或用户决策。
- 风险接受必须记录有权主体及其范围；审查者不能自行授予豁免。

## 6. 修正复审与收敛

- 比较上一轮已审候选与新候选，审查增量及其影响范围；处理旧问题同时寻找新问题。
- 核对最新完整变更清单与累计覆盖；新增路径、消费者、契约或基线变化必须补审。
- 作者声称修复仅记 FIX_REPORTED，实际核对后再改 VERIFIED；保留原 finding ID。
- 保留旧证据时记录原 subject_id 与仍适用的理由，不直接把标签改成新候选。
- 两轮修正复审后若同类阻断反复或关键未知不减，交回具体设计/验证问题并重定范围；不要无限追加审查。
- 达到轮次上限不产生 PASS。需要继续时在已有授权内明确新范围和预算，仅在决策权缺口处询问人。

## 7. 返回结果

使用 [审查结果模板](assets/review-result.md)，或返回具备同等信息的紧凑文本。
默认简短说明分轴结论、重要问题与未覆盖范围。接收方需要机器记录时使用 `work-result/v1`：schema_version、work_id、skill、outcome、subject、evidence、unresolved、changed_assumptions、next_action。
静态核查用 evidence.kind=source_inspection、status=OBSERVED；执行证据保留原始工具状态与版本。
需要结构化表达审查通过时，另填 evidence.assessment=PASS 并明确 scope；保留 OBSERVED，不把静态核查改名为运行通过。
历史材料用 HISTORICAL 并保留 raw_status、原日期和原 subject_id；不能写成本轮运行。

| Outcome | 使用条件 |
| --- | --- |
| PASS | 约定必需轴和覆盖范围已完成，没有未解决阻断项，所需独立性成立。 |
| FAIL | 存在已确认且未解决的阻断问题。 |
| INCONCLUSIVE | 已开始审查，但契约、覆盖、候选身份或所需独立性不足。 |
| BLOCKED | 必需材料、访问能力或权限缺失，无法开始。 |
| NOT_RUN | 尚未开展审查，或尚无可读取的设计、变更等候选材料。 |

用户明确只要求单轴时可对该范围结论；另一轴标 NOT_RUN，不宣称完整审查通过。
审查通过不代表运行验证、集成、合并或发布通过；本技能不自动发布评论或扩大外部写入权限。
