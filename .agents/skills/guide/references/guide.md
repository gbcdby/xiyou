# 工作技能使用指南

这套技能可跨项目、跨语言使用。先说明要解决什么、怎样算完成、希望做到哪一步；工具和授权沿用当前项目。

## 从目标开始

> 重连后出现重复消息。请复现并修复，完成必要检查和独立审查后开 PR，本次先做到可审查。

`deliver` 负责持续推进和调度，按需要选 worker。只要调查、设计或拆票时，直接说明终点；已有授权能继续时，不逐阶段重复确认。

## 入口怎样分工

协调与观察：

| 入口 | 用途 |
| --- | --- |
| `deliver` | 维护整体目标与任务图，调度并接收结果，推进到约定终点 |
| `collaborate` | 跨 Agent／harness 分派、沟通、交接、取消与恢复 |
| `brief` | 只读解释进度、设计变化、卡点与需要人决定的事 |

独立工作能力：

| Worker | 交付什么 |
| --- | --- |
| `worker-investigate` | 查证问题、目标、范围与未知 |
| `worker-design` | 行为、架构、共同约束与设计概览 |
| `worker-visual-design` | 美术方向、界面与组件规格，已确认设计的记录和复用 |
| `worker-plan-tickets` | 可执行 Tickets、依赖图与验收覆盖 |
| `worker-tla` | 设计模型、TLC 检查、反例及适用假设 |
| `worker-implement` | 指定 Ticket 的实际修改和必要自查 |
| `worker-ui-fidelity` | 按确认基准实现或修正界面，或只读核对视觉、交互与连续动效 |
| `worker-verify` | 指定候选与环境的真实检查证据 |
| `worker-review` | 独立审查需求和项目标准，跟进修正 |
| `worker-land` | PR、审查反馈、CI、冲突与授权内合并 |
| `worker-release` | 发布、部署和目标环境验收 |
| `worker-improve-workflow` | 针对具体问题评估、改进工作方法 |

你也可以直接使用任一 worker。技能数量不决定 Agent 数量：小任务可由一个 Agent 按需使用多个技能；并行任务按依赖、写入范围和实际能力分派。独立审查不能由作者换一个技能名后自评替代。

## Spec、Tickets 和共享记录

Spec 始终保留设计概览、共同约束、整体验收和任务目录／依赖图；Ticket 是可分配的执行单元。`worker-plan-tickets` 拆票，`deliver` 依据当前依赖和实际产物调度，`worker-implement` 按分派执行。

| 你现在需要什么 | 提示示例 |
| --- | --- |
| 只拆任务 | “用 worker-plan-tickets 拆解这份 Spec，明确依赖和完成条件，先不执行。” |
| 推进整份 Spec | “用 deliver 调度这份 Spec 的 Tickets，目标到合并，暂不发布。” |
| 只做一张票 | “用 worker-implement 完成 T3，遵守 Spec 当前版本，交回候选和检查证据。” |
| 改进界面设计 | “用 worker-visual-design 看现有界面和参考，提出两项优先改进，先不写代码。” |
| 对照设计验收 | “用 worker-ui-fidelity 对照确认图检查当前页面，先不修改，分别说明视觉和交互结果。” |

沿用项目 tracker、共享文档或已核实并选定的原生任务系统保存 Spec、Tickets 与依赖。每类事实只有一个权威来源，协作消息引用它；接入房间不自动迁移任务记录。

后续任务等待的是约定的前置产物，不只看标签或“做完了”的回复。全部 Tickets 达标后仍需整体集成验收。目标清楚、影响局部且低风险的小改动可直接实现、针对性检查并做项目要求的最小独立审查；未知消除后可回到短流程。按风险而非行数选择，既定 CI 与交付门槛仍适用。

自动模式同样保留大功能的 Spec／Tickets：可以逐批设计和拆票，先在权威来源保存本批记录再分派。写入受阻时留下待同步草案，只继续不依赖缺失记录的工作；没有实际任务引用或回读结果，不能声称共享记录已建立。

## CI/CD 怎样接入

沿用项目的检查与发布机制：`setup` 整理入口和自动推进范围，`worker-implement` 补配置，`worker-verify` 核验实际结果，`worker-land` 推进合并，`worker-release` 完成发布与交付位置验收。可直接从当前需要的步骤开始；没有远程 CI 或发布需求时，不强制搭建。推送、tag 或合并会自动发布的项目，也按实际效果核对既有授权。

## 你可以主动介入

| 人工入口 | 示例 |
| --- | --- |
| `auto` | “按项目流程推进这个需求，本次做到 PR 就绪。”；也可只修改项目默认流程 |
| `challenge` | “和我梳理这个大功能，先查现状，分批问关键取舍，把决定保存到现有 Spec 草案，先不实现。” |
| `steer` | “按方案 B 继续；任务 A 暂停，任务 C 照常做。” |
| `setup` | “接入这个项目，复用现有规则，只补必要适配。” |
| `guide` | “推荐一个入口，给我一条开始用的提示。” |

这些入口只由你主动发起，调度器不会自行调用。普通语言也可直接暂停、改向或设停点，无需记住技能名；实际停止要有宿主或工具证据。阅读 `brief` 不接受设计、不批准操作。

`challenge` 也可简短推敲，或“继续上次那份 Spec，只讨论尚未决定、现在能推进的部分”。它保存方向和待决问题，完整设计与实现任务由对应 worker 承接；auto 遇到确需人的取舍可直接给出短问题，不必自动启动这个人工入口。

`brief` 默认用短句、小表或关系图，先说成果、变化和待决事项。可追问某个子系统或具体例子，不必阅读所有 Agent 的对话。

## 安装与项目接入

安装让宿主发现技能；`setup` 适配项目，二者分开。使用目标平台支持的安装方式，保留完整技能目录、附带资源与许可，不覆盖未经核对的同名技能，不夹带凭据或个人任务记录。发现路径按目标宿主与项目规则选择。

初始化会复用已有流程文档，或从 auto 的唯一模板生成 `docs/agent-workflow.md`；以后明确的长期流程调整局部沉淀到同一文档，本次例外仍留在任务记录。`auto` 负责采用流程并启动／恢复，`deliver` 负责实际调度，不因增加入口建立第二套任务板。

项目长期事实保留在 `CONTEXT.md` 等既有知识入口；交付后任务状态与分支／worktree 清理分别核对，清理遵守已有授权和资源释放条件。

已有清楚约定时直接工作，setup 不是日常前置门。换项目需重新核对记录位置、工具链和交付规则，不沿用另一项目的权限或标签。

| 宿主 | 常见显式调用方式 |
| --- | --- |
| ChatGPT | 在支持技能选择的界面使用 `@` |
| Codex CLI／IDE | `/skills` 或 `$skill-name` |
| Claude Code／Cursor | `/skill-name`；插件入口可能带命名空间 |

以实际菜单和安装版本为准。找不到入口时检查安装位置、启用状态、名称冲突和宿主支持；配置正确不代表发现、调用或人工入口限制已实测。

## 怎样判断真的完成

验证只覆盖报告中的对象、版本和环境；模型检查、源码观察与真实运行分别看。PR 已创建、排队或设置自动合并仍需确认实际合并；合并不代表上线，发布和验收需要目标位置的证据。

接受设计、认可体验、授权合并和授权发布是不同决定；有效授权继续适用，沉默或看过不新增授权。没有代码托管平台、房间或某项可选技能时，现有能力仍可完成不受影响的工作；真实缺口应具体说明。

宿主语法以 [OpenAI](https://learn.chatgpt.com/docs/build-skills)、[Claude Code](https://code.claude.com/docs/en/skills)、[Cursor](https://cursor.com/docs/skills) 的当前官方说明与实测为准。
