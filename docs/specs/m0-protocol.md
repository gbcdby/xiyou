## 1. 范围与架构选择

- 一个 Session 只有一条权威事件序列；所有真人、核心 NPC、托管 AI 和定时任务都走同一提交入口。
- 首版采用单个 PostgreSQL 写库。每次修改先锁住对应 Session 行，串行校验并提交；进程内队列只改善调度，不承担唯一写入保证。不同 Session 不共用这把锁。
- 状态、事件、动作结果和待发布记录放入同一数据库事务。Redis 只用于在线状态、唤醒或推理队列，不作为提交成功或控制权的依据。
- 不在事务中等待 LLM、网络广播或客户端响应；数据库不可用时拒绝产生新事实，不退化到内存写入。
- 后端语言与 HTTP 框架保留实现自由；接口遵守本文即可。建议优先评估 TypeScript 以复用前端协议类型，具体依赖与版本在实现 Ticket 中固定，不以此新增框架或微服务承诺。

## 2. 身份、序号与状态

| 名称 | 语义 |
| --- | --- |
| `UserId` | 经服务端认证的真人账号；不进入 NPC 的角色识别与跨关关系判断 |
| `CharacterId` | 本 Session 的角色，开局后与真人账号绑定不可换角；核心 NPC 有独立角色 ID |
| `SessionId` | 服务端生成的本局实例 ID，关闭、删除后永不复用 |
| `principalId` | 服务端构造的提交主体：真人账号、核心 NPC、托管角色或系统；客户端不得指定或冒充 |
| `sessionSeq` | 唯一的 wire 事件顺序字段；单 Session 从 `1` 连续增长，初始游标为 `0`；替代旧示例的 `seq` |
| `baseSeq` | 发出动作时已完成同步的游标，不是锁、写权限或自动拒绝所有旧动作的依据 |
| `controlEpoch` | 角色提交授权的递增代次；与当前连接或 AI 主体绑定，防止旧控制者继续写入 |
| `resourceRevision` | 每个可变领域对象的递增版本，用于明确动作依据是否失效 |

序号和 epoch 在 JSON 中统一使用无前导零的非负十进制字符串，按数值比较，不按字符串字典序比较。时间为服务端 UTC 时间；客户端时间只可作诊断信息。协议首版使用 `schemaVersion: 1`，未知版本直接拒绝。

`sessionSeq` 由 Session 行中的事务计数分配：持锁读取已提交值 `n`，本事务生成 `k` 个事件时分配 `n+1…n+k`，并在同一事务更新该行。回滚同时撤销事件和计数更新；不得用 PostgreSQL `sequence` / `serial` 充当这个无缺口序号。

持久状态至少包含 `phase`、`sessionSeq`、角色绑定、控制权、区域、物品归属、已登记观察、NPC 信念/目标、承诺、终局事实及 `contentVersion` / `reducerVersion`。后两项固定本局规则，不能热替换正在进行的 Session。

## 3. 生命周期与终局

| 当前状态 | 允许的转换 | 权威条件 |
| --- | --- | --- |
| `Lobby` | `Running` | 房主发起；2–5 个真人绑定互不冲突的角色，满足关卡配置中的就绪条件 |
| `Lobby` | `Aborted` | 房主取消；保留终止原因 |
| `Running` | `Finished` | 规则判定成功、代价结局或到达本局截止时间；记录唯一 `endingCode` |
| `Lobby` / `Running` | `Aborted` | 授权的系统运维操作确认无法恢复，记录操作者与原因；不是模型可调用的工具 |
| `Finished` / `Aborted` | 无 | 仅可读取已授权的快照、结果与复盘；不能重新开启同一 Session |

开始后不增加真人或切换本关身份；原成员可以重连，少人局的角色能力在开局配置中确定。正常离线不终止 Session，仍按托管和截止时间推进。

处理新命令时，在取得 Session 锁后检查服务端时间。截止时间已到则先产生终局事件，再拒绝该命令；若未到且命令使终局条件成立，同一事务追加效果事件与最后一条 `session.finished`。同时竞争的命令按实际事务提交顺序裁定。

终局事务清除可提交控制授权，并使所有未完成 AI 决策失效。最后序号之后没有新的 WorldEvent；到期承诺不再执行、晚到消息不再广播成新对白。读取旧 Receipt 不产生新效果。

终局前已提交的事件仍可在终局后补发，其序号与内容不变。Receipt、发布进度等运行记录可以补写，但不能改变终局世界状态。

服务端时间检查使用不倒退的本局逻辑时间，后台定时器只负责唤醒同一入口；不能绕过事务直接结束房间。验证需覆盖“终局动作与普通动作同时到达”，而非只检查枚举值互斥。

## 4. 最小消息与结果

### 4.1 客户端动作

```json
{
  "schemaVersion": 1,
  "sessionId": "S1",
  "actorId": "C3",
  "clientActionId": "A-7b8d",
  "controlEpoch": "4",
  "baseSeq": "1008",
  "action": {
    "kind": "transfer_item",
    "itemId": "I7",
    "targetId": "C4",
    "expectedItemRevision": "2"
  }
}
```

`actorId` 只是请求值，服务端必须与可信主体、本局绑定和连接授权匹配。未知字段、重复 JSON 键、超出 schema 的值和非法工具名均拒绝。令牌、当前连接 ID、`principalId`、服务器时间与事件序号不能由请求正文指定。

### 4.2 已提交事件与 Receipt

| 记录 | 必需内容 |
| --- | --- |
| `WorldEvent` | `schemaVersion`、`sessionId`、`sessionSeq`、`eventId`、`causedBy`、服务端时间、类型、确定性 payload、服务端可见性元数据 |
| `ActionReceipt` | 去重键、语义载荷摘要、`actorId`、`Accepted` 或 `Rejected`、结果码、`observedSeq`、`actionEventRange`（允许为空）、可向该主体展示的结果 |
| `DecisionRecord` | AI 角色、`decisionId`、控制代次、决策代次、已授权 Observation 引用、读取的对象版本、截止时间、`Pending/Committed/Rejected/Expired/Cancelled` 状态 |
| `OutboxRecord` | 已提交区间或事件引用、发布状态；不复制一份可自行修改的世界事实 |

`eventId` 唯一键为 `(sessionId, sessionSeq)`，对外可编码为 `S1:E1009`。`causedBy` 指向原始动作或系统命令，AI 动作另关联 `decisionId`。事务内多条事件占用连续区间。

`observedSeq` 是作出该 Receipt 时事务提交后的世界游标，不代表客户端已经同步。`actionEventRange` 仅记录本动作产生的事件；若动作触发正常终局，则包含最后的终局事件。命令因超时被拒绝时，该范围为空，但同事务系统截止事件可使 `observedSeq` 前进。返回旧 Receipt 时保留原值，当前游标通过同步接口获取。

说话事件证明“某角色说过这些话”，不证明话中断言为真。`ClaimRecorded`、`ObservationRecorded`、`BeliefUpdated` 与物品转移等世界效果使用不同事件类型；后者不能由对白或模型返回的 `beliefUpdates` 直接构造。

`Accepted` 表示权威事务已提交，可能只有观察记录或已确认无变化；只有读取了完整事件区间/新快照，客户端才能把投影视为已同步。`Rejected` 是本次动作的确定结果，不表示网络故障。`Pending/Unknown` 仅为调用方状态，不是已提交 Receipt。

## 5. 幂等与结果未知

去重键为 **`(sessionId, principalId, clientActionId)`**；AI 使用服务端生成的 `decisionId:submit` 作为整包动作 ID，系统任务使用稳定原因键。角色 ID 包含在语义摘要中，不能用同一 ID 对另一个角色重新执行。

语义摘要覆盖版本、Session、角色、`controlEpoch`、`baseSeq` 和动作全部字段；服务端先按 schema 规范化，再以固定键序编码。认证令牌、连接 ID、传输重试次数不参与摘要。**原 ID 重试必须保留原语义载荷，包括旧 epoch**；不能自动把旧意图改成新授权动作。

| 情形 | 行为 |
| --- | --- |
| 当前认证失败、无本局访问权或角色结果不可读 | 在读 Receipt 前拒绝；不暴露它是否存在 |
| 去重键已存在，摘要相同 | 返回原 Receipt；不再执行，不因当前终局或 epoch 改变而改写原结果 |
| 去重键已存在，摘要不同 | `ACTION_ID_REUSE`；不覆盖原 Receipt |
| 去重键不存在，当前领域校验不通过 | 保存 `Rejected` Receipt；同 ID 重试返回相同结果 |
| 解析/认证失败，或事务未能确定提交结果 | 不伪造确定 Receipt；调用方保留原 ID 查询或重试 |
| 已返回拒绝，玩家看过新状态后仍想尝试 | 显式产生新动作 ID 和新的前置条件，不篡改旧请求 |

Receipt 在 Session 存续期间不按短 TTL 删除。归档时连同事件保留；不存在或已删除的 Session ID 统一返回 `SESSION_GONE`，不确认其历史是否存在，不重建同 ID 房间、不重新执行动作。读旧结果仍需当前认证、Session 访问与相应角色结果权限，不能将其他角色的私密结果作为去重响应返回。

若进程在 `COMMIT` 后、ACK 前退出，客户端无法据超时判断失败；应查询该 ID 或原样重试。若数据库连接在提交时中断，服务端也先标记结果未知并查同一键，不创建新 ID 补做。前端以“等待确认”显示，不能通过乐观 UI 发放物品。

## 6. 原子提交与发布

一次提交的线性化点是 **PostgreSQL 事务成功 COMMIT**。具体顺序如下：

1. 校验消息结构、认证与本局访问，建立可信执行上下文；不接受客户端提供的权限标签。
2. 开启事务并锁住 Session 行；锁取得后重读当前行及关联状态，重新检查授权与绑定，查 Receipt。命中则返回原结果或 ID 冲突。首版可用 `READ COMMITTED`，但所有本局修改路径都必须遵守同一锁约定。
3. 读取最新权威状态，处理已到期终局，再检查角色授权、epoch、动作前置条件和领域规则。
4. 生成确定性事件；校验后通过 reducer 得到新状态。随机结果与所用时间写入事件，回放不能重新抽样或调用模型。
5. 在同一事务保存新状态、连续事件、Receipt、outbox；事件 `(sessionId, sessionSeq)` 和 Receipt 去重键有数据库唯一约束。拒绝本身只保存 Receipt、不占新序号；步骤 3 判定已到期时，同事务系统终局仍保存事件、推进序号和发布记录，拒绝动作的 `actionEventRange` 为空。
6. COMMIT 成功后发 ACK，唤醒发布器；发布器从已提交事件生成每个观察者的过滤消息。

任一事务内失败全部回滚，不能提前广播、先改缓存或先 ACK。广播失败不撤销已提交效果；outbox 可重试、可重复送达，消费端按序号去重。不得声称网络恰好一次送达；保证的是同一动作至多一次提交效果。

发送完成标记不能替代客户端游标。发布器崩溃或 Redis 丢失时，以持久事件和客户端最后游标补发；单个进程恢复后从数据库重建状态与未完成发布。

PostgreSQL 的[事务](https://www.postgresql.org/docs/current/tutorial-transactions.html)、[行级锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[隔离语义与序列回滚限制](https://www.postgresql.org/docs/current/transaction-iso.html)及[唯一约束](https://www.postgresql.org/docs/current/ddl-constraints.html)提供所需基础能力；这些官方资料不证明本项目实现已正确。Socket.IO 的[默认投递保证](https://socket.io/docs/v4/delivery-guarantees/)也不能代替上述应用协议。来源读取日期为 2026-11-11。

## 7. 旧状态、物品争夺与前置条件

- `baseSeq > 当前 sessionSeq`：`FUTURE_BASE_SEQ`。`baseSeq` 较旧不会单独导致拒绝；校验当前可见性、对象版本与动作要求。
- `move` 校验当前区域连接及移动能力；`inspect` 校验当前接近关系和可感知对象；不要求无关对象版本相同。
- `transfer_item` 必须带 `expectedItemRevision`；当前持有者仍是该角色、版本匹配、目标可接收且物品可转移时才提交。`take_item` 同理检查当前场景位置与版本。
- `use_item` / 修复等效果动作必须声明涉及物品和目标版本；缺少必需前置条件即拒绝，不能默认为“按最新对象随便做”。内容规则再校验能力、消耗与目标。
- `share_evidence` 必须引用发送者已实际获得且允许传播的证据；生成新的合法传播事件，不修改原证据或历史可见性。
- `speak` / `make_claim` 只记录可听见的陈述；请求、承诺、接受条件与实际执行分别记录。具体关卡动作的允许条件由版本化 content 规则补充，不能越过本文事务。

每件唯一物品具有且只有一个位置：角色持有、场景位置或已消耗。成功转移同时移除原位置并增加新位置，版本递增。模型必须检查两个竞争动作的授权/提交结果与实际持有集合，不能仅以单值 owner 类型检查代替竞争安全性。

对象不存在或不可见统一返回 `TARGET_UNAVAILABLE`；可见对象版本冲突返回 `STALE_PRECONDITION` 并要求同步，不回传隐藏持有者、完整对象或其他房间信息。跨 Session 的 ID 永远不能参与本局校验。

## 8. 角色控制与断线交还

真人角色有 `mode`、`controlEpoch`、`activeConnectionId`、`graceDeadlineAt`；提交必须同时匹配 mode、可信主体、epoch 和当前连接。单看客户端上传的 epoch 不能获得权限。

| 转换 | 同一权威事务中的效果 |
| --- | --- |
| 首次获得真人控制 | 绑定本局角色与当前连接，进入 `HumanControlled`，分配 epoch |
| 当前连接断开/心跳超时 | 只有携带的连接与 epoch 仍匹配才转 `GracePeriod`；epoch 递增、撤销旧连接，设宽限截止时间 |
| 宽限到期 | 若仍是同一宽限代次，转 `AIProxyControlled`，epoch 递增；创建受限 AI 决策 |
| 宽限/托管中原账号重连，或原账号显式接管 | 校验原角色绑定；转 `HumanControlled`，epoch 递增、绑定新连接并使旧 AI 决策失效 |
| Session 终局 | 撤销所有提交授权，失效未完成决策；原有事实仍可读取 |

宽限期建议默认 **30 秒**，是可调整配置，值在开局固定。宽限期间该角色没有世界写入者，其他人和 NPC 继续活动。离线检测只是入队请求；迟到的旧连接断开通知不能撤销已重连的新连接。

同账号的新连接先以只读模式接入；已有其他活跃控制连接时，`control.resume` 返回 `CONTROL_HELD`，只有明确的 `control.take` 请求才替换现有连接。两次接管竞争按事务顺序处理，只有最后一个当前代次可提交，较早的成功响应也不代表其授权永久有效。控制命令 nonce 的重复响应不会重新换绑；新物理连接需要新的控制请求。

核心 NPC 使用独立服务主体和 `CoreNPCControlled` 授权，不进入真人交接链；其控制代次同样在终局撤销，客户端不能请求该授权。

代理继承本角色已允许获知的场景信息、物品和承诺，但不读取真人私人频道。首个切片代理仅允许安全移动、观察、公开询问/等待；禁止物品转移/消耗、达成终局的承诺和重大不可逆选择。总设计中的“维持游戏必需”例外在本切片不开放，由后续 Spec 单独定义；不由模型临时解释。

真人返回前已提交的代理效果保留并展示；尚未提交的代理意图因 epoch 失效拒绝。收到旧动作的重复请求时，已有 Receipt 仍可依授权返回，但不能产生第二次效果。

## 9. 授权投影、过滤流与重连

### 9.1 可见性

每条事件提交时由服务端确定可见主体集合或确定性策略，分别区分真人观察、核心 NPC 感知与托管代理可读内容。观察者的房间、角色、区域与知识资格来自权威状态，不信任请求声明。

日志必须保留足以重建发生时可见性的受众或版本化策略依据；不能用当前所在区域过滤历史日志。进入区域等资格变化产生新的授权观察/投影效果，允许读取当时可见的当前状态，但不补发未获授权的旧事件。

人类可见结果不自动成为 NPC Observation。NPC 或代理也不能因为与某个真人共用 CharacterId 而取得私人频道权限。Prompt 不是过滤层，Model Gateway 只能接收过滤完成的上下文。

历史事件按发生时已授予的资格读取，后来走入区域不能倒看过去的私密对话。合法传话、出示证据或公开揭示产生新事件，明确来源与接收者；不得改写旧事件受众。已合法获知的事实可进入本角色记忆，不因离开区域自动遗忘。

快照来自相同规则构造的**角色授权投影**，包含该角色当前可见状态与合法积累的知识；不是把完整世界 JSON 发给客户端再隐藏 UI。它不包含其他角色信念、秘密、未来剧情或全量决策调试数据。

当前可见状态与历史知识分开存储，历史知识带来源游标；离开后不应把物品的新秘密位置当成已知。实时投影也须更新可见字段的加入/移除，才能与同一游标的授权快照一致；传输 DTO 不携带持久事件的内部受众或主体凭据。

### 9.2 消息区间与游标

```json
{
  "type": "world.batch",
  "sessionId": "S1",
  "viewId": "C3-human-v1",
  "fromExclusive": "1008",
  "throughSeq": "1011",
  "events": [
    {"sessionSeq": "1010", "eventId": "S1:E1010", "kind": "item.transferred", "payload": {"itemId": "I7", "to": "C3"}}
  ]
}
```

该消息覆盖 `(1008,1011]` 的完整提交区间，但只携带授权事件或安全投影效果。1009、1011 不可见时没有占位正文，也不构成丢包；空 `events` 仍可推进 `throughSeq`。不得把隐藏事件的类型、主体、受众或 payload 填进跳过标记。

- 首次连接返回过滤 `snapshot + snapshotSeq + viewId`。状态与序号来自同一个已提交快照；M0 可将完整权威状态与当前 `sessionSeq` 同行保存后在服务端投影。
- 客户端只有在 `fromExclusive == 本地 cursor` 时，按数值序应用可见效果并将游标原子推进到 `throughSeq`；同批次不可只应用前半段就保存末游标。
- `throughSeq <= cursor` 的整批重复直接忽略；未来批次或重叠批次不猜测补全，丢弃并从当前 cursor 请求新的区间。
- 服务端补发只读取同一 Session 已提交日志，区间跨度固定上限；不能因为某段无可见事件就返回“无更新”而不推进游标。
- 日志已归档、游标超出 head、投影版本不同或换角色时返回 `RESYNC_REQUIRED`，客户端清除旧投影与旧待应用队列，重新取授权快照。
- 当前身份失效、权限撤销或连接换绑时停止旧订阅；订阅上的 `viewId` 由服务端绑定，不能自由指定另一个角色。

本切片的秘密边界保护内容、身份与信息流权限；全局游标会暴露本局事件计数/节奏，不承诺隐藏流量元数据。测试不得把不同角色的私有投影要求成完全相同：应比较相同 cursor 的公共状态，以及各自投影与服务端授权结果的一致性。

## 10. AI 意图、过期决策与回放

推理调度器在事务外请求模型；事先保存 `DecisionRecord`，绑定当前角色、控制 epoch、决策代次、可用工具、Observation 引用及会影响该决定的对象版本。决策 ID 和工具权限由服务端生成。

规范化后的 `ProposedIntent` 包含 `decisionId`、有序 `toolCalls`、可选对白及候选信念更新；整包只是一条内部命令，语义摘要覆盖整个规范化包。它按工具顺序在事务内候选状态上模拟和校验，全部通过才原子保存效果、Receipt 与决策结果。任一工具失败则整包拒绝，不先提交或广播对白；`toolCallIndex` 只用于事件因果关联，不能拆开重试/提交。

读取的外部对象版本在批首与权威状态比较，由服务端 DecisionRecord 提供，不能由模型覆盖。前一工具引起的批内版本变化按候选状态继续计算，不误判为外部过期，也不能掩盖批首已存在的版本冲突。决策状态在同一 Session 锁下只从 `Pending` 收束一次；终态重复回调只读已保存结果。

新计划替代、取消、控制权交还和终局使旧决策代次失效；运行中的 LLM 调用即使不能物理取消，其返回也不能越过提交校验。模型返回的 `decisionId` 等字段不能覆盖服务端原记录。

提交前同时检查：Session 仍可写、控制代次有效、决策仍待处理、未超时、读取的相关对象/目标/信念版本仍匹配、工具允许、当前领域条件成立。无关事件使 `sessionSeq` 增长不必废弃决定；相关证据或目标失效则返回 `DECISION_STALE` 并重新观察。

模型的 `beliefUpdates` 只是候选。确定性策略确认其依据属于该 NPC 已登记 Observation，并只生成信念更新事件；它不能生成新世界事实。对白中未证实的内容保持 Claim 身份；无法证明全部自然语言真实，不把这项能力纳入协议保证。

建议普通决策超时默认 **10 秒**，可在内容配置中调整；超时、非法 JSON 或无合法工具时，将该决策收束为 `Expired` 或 `Rejected`，安排受限的等待/重新观察行为。fallback 是带稳定原因键 `decisionId:fallback` 的独立系统命令，仍检查当前 epoch、终局和权限；后续推理分配新 decisionId，不能复活已收束决定。

同一决策的重复回调使用固定动作 ID 去重；不能重复发言或重复消费物品。失败、重试及决策依据记录在受限调试数据中，面向玩家只显示已授权的世界效果和必要状态。

重放使用固定 content/reducer 版本、初始状态与已提交事件；模型输出、时间、随机选择只取事件中已经记录的结果。重放不再次调用 LLM、不触发 outbox 或外部效果；结束时核对状态摘要与 `sessionSeq`。

## 11. 接口与错误边界

M0 定义语义，M1 才提供网络实现。HTTP / Socket.IO 共用同一个命令处理器，不维护两套校验规则。

| 入口 | 语义 |
| --- | --- |
| 创建 / 加入 / 角色领取 / 开始 | Lobby 操作；创建请求用可信 UserId 与创建 nonce 去重，其余写操作经本局命令事务 |
| `player.action.request` | 提交本文动作 envelope；成功或领域拒绝返回 Receipt |
| `GET /sessions/{id}/actions/{clientActionId}` | 按当前可信主体查本人动作结果；不存在表示尚无确定记录，不证明未来不会提交 |
| `GET /sessions/{id}` | 当前角色授权 snapshot；跨房间或未授权访问拒绝 |
| `sync.request` | 携带 `viewId` 和 cursor，返回连续区间或要求重新同步 |
| `control.resume` / `control.take` | 原账号重连／显式替换连接；有独立 nonce，按当前主体与角色绑定幂等处理 |

`INVALID_MESSAGE`、`UNAUTHENTICATED`、`FORBIDDEN` 属于进入领域提交前的拒绝；`SESSION_NOT_RUNNING`、`STALE_CONTROL`、`TARGET_UNAVAILABLE`、`STALE_PRECONDITION`、`ACTION_ID_REUSE`、`DECISION_STALE`、`DECISION_EXPIRED` 为确定原因。错误详情仅包含当前主体有资格知道的信息。

可重试的连接/数据库故障返回 `OUTCOME_UNKNOWN` 或无 ACK；不可将其转成一次新的领域动作。RPC ACK、WorldEvent 投递和客户端同步完成是三个不同事实。

## 12. 验收与实现义务

以下是待执行的 M0 验收；模型与真实实现需分别取得证据。每项行为至少有一个可到达的正常样本和一个能暴露相应缺陷的失败样本。

| 验收 ID | 可观察行为与失败判据 |
| --- | --- |
| M0-AC-01 | 所有写主体经同一权威入口；并发提交形成唯一连续事件序列，重放状态等于持久状态；无跨房间修改 |
| M0-AC-02 | 两人竞争同一物品最多一个满足原前置条件并提交；位置集合不重复、不丢失，败者不产生消费或转移效果 |
| M0-AC-03 | 同键同载荷重试返回原 Receipt 且副作用次数不增加；异载荷不能覆盖；归档/删除边界不导致重做 |
| M0-AC-04 | 在提交前、提交后 ACK 前、广播中分别故障注入；只出现全回滚或已提交可恢复，不能产生孤立事件/状态/收据 |
| M0-AC-05 | 旧 baseSeq 的无关变化不误拒绝；目标版本变化拒绝，未来 baseSeq 拒绝；同一 ID 不能靠更新字段重新执行 |
| M0-AC-06 | 断线、宽限到期、双连接、接管与迟到断开任意交错，不存在两个可提交控制者；旧连接和旧代理结果失效 |
| M0-AC-07 | 人工终局条件、超时与普通动作竞争时只形成一个终局；终局后不执行新动作、承诺或 AI 回调 |
| M0-AC-08 | 含隐藏事件的批次可正确推进游标；重复、丢失、乱序与重连后投影与服务端一致；不会把可见性洞误当漏事件 |
| M0-AC-09 | 当前认证与角色权限保护快照、流、Receipt、错误及 NPC 上下文；未授权秘密不得直接投递，合法传播有新事件依据 |
| M0-AC-10 | 非法 JSON、越权工具、虚构 Observation、过期/取消决策和模型超时不产生原意图效果；多工具全成或全拒，fallback 不绕过相同检查 |
| M0-AC-11 | Fact / Claim / Belief 分离，回放不重新推理；NPC 重要行动可追到真实观察、目标、决定与提交结果 |
| M0-AC-12 | 关键模型提供规模、状态数下限、BFS/死锁/liveness 配置、每项不变量负对照和实现映射；缺失证据不得标为模型通过 |

优先模型：Ownership、RoleHandoff；将相应的 Receipt、事务阶段、显式授权、终局与迟到消息纳入状态，不只验证单字段 TypeOK。Reconnect/SecretVisibility 和其他模块随其实现阶段补齐；对所有模型沿用工程约定的负对照要求。

安全性允许任意重试、丢包、乱序、进程重启与推理迟到。活性只在数据库最终可用、运行中的服务能公平处理已就绪工作、授权客户端持续重试且网络最终送达的假设下讨论；不承诺永久断网或无限失效新信息下必然收到结果/完成 AI 决定。

同一数据库的事务持久性、认证系统正确性、内容规则满足自身业务约束属于环境/实现假设，不能由小规模 TLA+ 模型代为证明。数据库故障后可能暂停服务；模型预算、真实部署配置、库版本与性能证据由实施和验证任务固定。

改变去重范围、角色换绑、终局语义、可见性规则、并发写入或网络字段时，须回到本规格并重评模型与消费者；具体表结构、索引细节与模块内部语言组织可在满足这些义务的前提下自主选择。
