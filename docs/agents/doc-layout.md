# 文档布局与维护边界

文档写入前按本文件确定归属。新增文件名使用英文，正文使用中文。

## 已有入口

| 路径 | 职责 |
| --- | --- |
| `README.md` | 项目介绍与阅读入口 |
| `AGENTS.md` | 必须常驻的规则与按需读取入口 |
| `初步设计文档.md` | 产品与总体技术依据，保留原文件名兼容现有引用 |
| `docs/README.md` | 文档索引与权威关系 |
| `docs/project-status.md` | 带日期的当前基线、路线与下项工作 |
| `docs/engineering.md` | 工程边界、领域命名与验证要求 |
| `docs/agents/` | 项目工作流、GitHub 记录、标签与文档布局 |
| `docs/specs/README.md` | 细化 Spec 索引与状态约定 |
| `docs/design-direction/` | 美术、UI/UX 共性、参考来源与视觉证据 |
| `.agents/skills/` | 通用工作技能；项目专有决定写回项目文档 |
| `.agent-output/<agent-or-task>/` | 临时材料、日志、截图，不作为正式证据链接 |

## 按需新增

- 细化 Spec：`docs/specs/<slug>.md`，写清状态、总设计依据、整体验收与 GitHub 任务入口。
- 工程调研：`docs/research/<topic>.md`，包含问题、结论、来源与适用范围。
- 视觉调研：`docs/design-direction/references/research/<topic>.md`。
- 代码、协议、正式模型与关卡配置：按[工程约定](../engineering.md)在真正实现时建立目标目录，不预先把空目录当成果。
- 需要独立保留且已有文档难以承载的重要架构决定，可在 `docs/adr/` 建立记录，并从有效 Spec 引用；普通决定直接更新所属文档。

不为开始任务强制新增 `CONTEXT.md`、ADR 或另一套看板。被拒绝的范围写在相关 Spec 或 Issue 的决定中，保留原因与来源。

## 维护规则

1. 一个事实尽量有一处正式归属；索引、路线表和 Issue 用链接关联，不复制整份正文或维护平行状态。
2. 用户新决定按适用范围修订旧结论，写明日期与依据。设计草案、接受的方案、当前实现和检查证据分别标记。
3. 文档声明“已有文件”“已完成”“已验证”前核对真实对象。外部参考缺失时记录缺口，不补造编号、素材或历史成果。
4. 正式文档不引用临时产物；需要保留的证据放进对应版本化目录、GitHub PR/Issue 或可访问的产物记录。
5. 本次文档整理完成后检查相对链接、技能名称、JSON 与计划/现状措辞；工程行为测试仅在涉及实际代码时安排。
